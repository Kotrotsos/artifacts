1. Install and run idle

Goal: get Symphony built and running with no tracker yet Time: 2 min

Set up the environment

# From the repo root
python3 -m venv .venv
. .venv/bin/activate
pip install -e ".[dev]"

Confirm the CLI is on PATH

symphony --help
# prints the run subcommand, --workflow, --port, --bind, --log-level

Run the test suite as a smoke check

.venv/bin/python -m pytest -q
# 54 passed in 0.2s
Why it matters. The tests lock down the spec invariants: workspace sanitization, candidate sort order, backoff curve, Linear payload normalization, strict Liquid rendering. If they pass, the orchestrator itself is healthy.

2. Connect to Linear

Goal: see a real poll tick succeed against the Linear API Time: 5 min

Issue a Linear personal API key

Go to linear.app/settings/api and create a personal API key. Save it to a file outside the repo, or to s-key.key (already in .gitignore).

Find your project slug

curl -s -X POST https://api.linear.app/graphql \
  -H "Authorization: $(tr -d '\n\r ' < s-key.key)" \
  -H "Content-Type: application/json" \
  -d '{"query":"query{ projects(first:10){ nodes{ name slugId } } }"}' \
  | python3 -m json.tool

Wire it into WORKFLOW.md

tracker:
  kind: linear
  api_key: $LINEAR_API_KEY
  project_slug: 9919061cee92   # your slugId
  active_states:
    - Todo
    - In Progress
  terminal_states:
    - Done
    - Canceled
    - Duplicate

Start Symphony

export LINEAR_API_KEY="$(tr -d '\n\r ' < s-key.key)"
symphony --workflow ./WORKFLOW.md --port 8765

Two POST /graphql 200 OK log lines on the first tick means you are connected.

3. Author the per-issue prompt

Goal: write a Liquid template that the agent receives on turn one Time: 5 min

Everything after the YAML front matter is the prompt template. Strict Liquid rules: unknown variables and unknown filters fail rendering, which is what you want, mistyped {{ issue.titel }} should error loudly rather than silently produce an empty string.

# Issue {{ issue.identifier }}: {{ issue.title }}

State: {{ issue.state }}
Priority: {{ issue.priority }}
URL: {{ issue.url }}

## Description

{{ issue.description }}

{% if issue.labels.size > 0 %}
Labels: {% for label in issue.labels %}`{{ label }}`{% unless forloop.last %}, {% endunless %}{% endfor %}
{% endif %}

{% if attempt %}
This is continuation attempt {{ attempt }}. Resume from the most recent
partial progress rather than starting over.
{% endif %}

Preview the rendered prompt without dispatching

.venv/bin/python -c "
from symphony.workflow import load_workflow
from symphony.prompt import StrictPromptRenderer
from symphony.domain import Issue
wf = load_workflow('WORKFLOW.md')
issue = Issue(id='i', identifier='INC-5', title='Demo',
              state='Todo', labels=['feature'])
print(StrictPromptRenderer().render(wf.prompt_template, issue=issue))
"
First turn vs continuation. Symphony sends the full template only on turn one. Subsequent turns inside the same worker run reuse the live agent thread and receive a short continuation message. Use {% if attempt %} to add retry-specific guidance to the full prompt.

4. Bootstrap workspaces with after_create

Goal: clone your repo into each new per-issue workspace Time: 3 min

The after_create hook runs only on first creation of a workspace. Symphony reuses the directory across runs, so this is the right place for one-shot setup. Failure here aborts workspace creation and removes the partial directory.

hooks:
  after_create: |
    set -euo pipefail
    git clone --depth 1 git@github.com:your-org/your-repo.git .
    cp .env.template .env
    pip install -r requirements.txt
  timeout_ms: 120000   # bump for slow installs

Test the hook by hand

# cwd will be the workspace path, SYMPHONY_WORKSPACE points at it
SYMPHONY_WORKSPACE=/tmp/test-ws \
  bash -lc 'cd "$SYMPHONY_WORKSPACE" && # your script here'

5. Pre-flight each run with before_run

Goal: refresh dependencies and pull latest main before every agent turn Time: 3 min

This hook runs before every agent dispatch, not just the first. Failure aborts the current attempt and triggers exponential backoff retry.

hooks:
  before_run: |
    set -euo pipefail
    git fetch --all --prune
    git checkout main
    git reset --hard origin/main
    git clean -fd
Destructive resets. The spec lets you reuse workspaces across runs. A hard reset throws away any in-progress agent work. Prefer a soft strategy (git pull --ff-only on a branch) unless your workflow explicitly starts each turn from a clean state.

6. Monitor live runs over HTTP

Goal: dashboard the orchestrator without parsing logs Time: 2 min

Set server.port in WORKFLOW.md or pass --port. Three endpoints:

EndpointPurpose
GET /healthzLiveness probe for load balancers.
GET /snapshotRunning rows, retrying rows, token totals, rate-limit snapshot, live config.
POST /reloadForce a defensive workflow reload now (no need to wait for the watcher).
 
curl -s http://127.0.0.1:8765/snapshot | python3 -m json.tool
curl -X POST http://127.0.0.1:8765/reload

7. Tune concurrency caps

Goal: cap parallel agents globally, per state, and per worker host Time: 3 min

Three caps apply in sequence (global, then per-state, then per-host). A candidate must clear all three. Per-state keys are case-insensitive, invalid entries are silently dropped.

agent:
  max_concurrent_agents: 10           # global
  max_concurrent_agents_by_state:
    "Todo": 6                            # cap fresh work
    "In Progress": 4                     # cap continuations

worker:
  ssh_hosts:
    - build-01.internal
    - build-02.internal
  max_concurrent_agents_per_host: 2     # 4 hosts × 2 = 8 max
Live tunable. Edit WORKFLOW.md while Symphony is running. The watcher re-applies caps on the next tick, no restart needed.

8. Hot-reload WORKFLOW.md

Goal: change config without restarting the service Time: 2 min

Symphony watches the workflow file via watchfiles.awatch. Edits trigger _reload_workflow_defensive, which re-validates and swaps the runtime config in place. A malformed reload keeps the last known good config and emits one log line.

# Edit poll interval down to 5s
sed -i.bak 's/interval_ms: 30000/interval_ms: 5000/' WORKFLOW.md

# Force a reload immediately rather than waiting for the watcher
curl -X POST http://127.0.0.1:8765/reload

# Confirm
curl -s http://127.0.0.1:8765/snapshot | python3 -c \
  'import sys,json; print(json.load(sys.stdin)["config"]["poll_interval_ms"])'
# 5000
Live sessions keep the old config. A workspace that is mid-turn finishes on the old codex.* settings. Restart the service if you need a hard cutover.

9. Recover from stalled agents

Goal: kill workers that go quiet and queue a retry Time: 2 min

Every tick, Symphony measures the time since each running worker's last agent event. If it exceeds codex.stall_timeout_ms, the worker is terminated and an exponential-backoff retry is queued.

codex:
  stall_timeout_ms: 300000   # 5 minutes (default)
  turn_timeout_ms: 3600000   # 1 hour per turn
  read_timeout_ms: 5000      # sync request/response

What you see in logs

level=warning event=stall_detected issue_identifier=INC-7 outcome=terminating
level=info event=retry_scheduled issue_identifier=INC-7 attempt=2 delay_ms=20000

Set stall_timeout_ms to 0 or a negative number to disable stall detection entirely. Useful when the agent is allowed to think silently for arbitrarily long.

10. Expose a custom tool to the agent

Goal: let the agent call your code via a JSON-RPC tool Time: 10 min

The agent client dispatches item/tool/call notifications through a name-to-handler map. Each handler is async def(tool_name, payload) -> dict and returns a structured response, by convention {"success": bool, ...}.

Define your handler

# symphony/my_tool.py
async def deploy_preview(tool_name: str, payload: dict) -> dict:
    branch = payload.get("branch")
    if not isinstance(branch, str) or not branch:
        return {"success": False, "error": "branch required"}
    # call out to your deploy service, return the resulting URL
    return {"success": True, "preview_url": f"https://preview/{branch}"}

Register it in the orchestrator

# symphony/orchestrator.py, inside _run_worker where CodexClient is built
from .my_tool import deploy_preview

client = CodexClient(
    ...,
    tool_handlers={
        "linear_graphql": LinearGraphqlTool(self._cfg.tracker),
        "deploy_preview": deploy_preview,
    },
)

Unknown tool names return a structured unsupported_tool_call failure automatically, so you only ever add the names you actually implement.

Built-in tool. linear_graphql ships in the box. It executes a single GraphQL operation against Linear using the same auth Symphony uses for polling. Use it from the prompt to move tickets between states without giving the agent raw API tokens.

11. Track Linear edits back to Symphony

Goal: understand exactly when an edit in Linear becomes visible to Symphony Time: 5 min

Symphony has no webhooks. Everything is poll-driven. Edit a ticket in Linear and the change becomes visible on the next tick, at most polling.interval_ms later. What happens after that depends on what you changed and whether a worker is already running on that issue.

Diagram 1: The poll-tick loop

One tick is the full cycle below. Reconciliation runs first so terminated workers free their slots before dispatch evaluates eligibility.

Diagram 2: What happens when a state changes mid-run

Every tick, Symphony refreshes the state of currently-running issues. The action depends on which bucket the new state falls into.

Diagram 3: Edit-propagation timeline

A state edit takes effect within one tick. A content edit (title, description, labels) is read at the moment Symphony fetches candidates, but a worker that is mid-turn keeps the prompt it was originally rendered with. The content edit only reaches the agent on the next fresh dispatch.

Verify in one place. Open curl -s http://127.0.0.1:8765/snapshot | jq '.running[] | {issue_identifier, issue_state}' while you edit. The state field updates within one polling.interval_ms window.
