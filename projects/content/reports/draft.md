*AGENTS.md taught your agent to behave. SKILL.md taught it to specialize. DESIGN.md teaches it to look like your brand. Here is the operational reality the introductions skip.*

---

In April 2026, two things happened in quick succession. Google open-sourced an internal specification called DESIGN.md, a plain-text format for describing a design system to AI coding agents. Two days later, a team called VoltAgent published a curated collection of 423 brand systems in that format. Five weeks later, the collection had 73,000 GitHub stars.

That kind of star velocity is not noise. It is the signal that a structural gap had finally found a name.

The gap is this: AI agents have become very good at writing code. They have remained unreliable at staying visually consistent across a project. Five pages of the same app, generated by the same agent, can end up with five different design systems. The buttons drift. The grays shift. The spacing argues with itself. Each page looks fine in isolation. Together, they look like five different products.

This is a context failure, not a model failure. The agent has no persistent reference for what your design looks like, so it generates a fresh reasonable default every time. Reasonable defaults drift.

DESIGN.md is the file that holds that reference. The introductions have covered what it is. What I want to give you is the operational reality the introductions skip: where DESIGN.md sits in the larger instruction-file family, the minimum viable version (which is shorter than you think), the token cost, the CLI tooling, the four ways it still breaks, and what to do in the next thirty days if your team has not adopted one.

## The bigger picture: three layers of AI instruction

Most coverage discusses DESIGN.md as a standalone artifact. That framing misses the structural shift. AI instruction files have split into three layers, each handling a distinct concern.

![Three layers of AI instruction stacked, with AGENTS.md at the top for behavior, SKILL.md in the middle for capability, and DESIGN.md at the bottom for visual identity](diagram-1-layers.png)

**AGENTS.md** sits at the top. It tells the agent how to behave in this project. Coding conventions, escalation rules, what to assume about the stack, what to never touch. It was donated to the Linux Foundation in December 2025 and is jointly maintained now by OpenAI, Google, Cursor, and the Amp team. If you have a CLAUDE.md, .cursorrules, or copilot-instructions.md, you are running an AGENTS.md by another name.

**SKILL.md** sits in the middle. It tells the agent how to do one specific task well. Skills are folders containing instructions, optional scripts, optional reference files. Anthropic shipped them in late 2025. Skills load lazily based on a description field that Claude reads to decide whether to activate the skill. Most teams use them for repeatable analytical or operational work.

**DESIGN.md** sits at the bottom. It tells the agent how the output should look. Colors, typography, components, spacing, do's and don'ts. Google Labs released the spec under Apache 2.0 in April 2026.

The three are complementary. AGENTS.md governs behavior across the project. SKILL.md adds task-specific expertise on demand. DESIGN.md constrains visual choices for every UI artifact the agent produces.

The framing matters because most teams have written one or two of these files and not the third. The third area, predictably, is where the agent drifts. Teams with strong AGENTS.md files write clean code that looks visually inconsistent. Teams with strong DESIGN.md files generate beautiful UI that violates their architectural conventions. The trio is the actual unit of analysis. Adopt them together, or accept that one corner of your output will keep drifting.

## What DESIGN.md actually is

A DESIGN.md file is plain markdown. It has two parts.

![Anatomy of a DESIGN.md: YAML frontmatter on top with token values, markdown body below with section headings for theme, colors, typography, components, and rules](diagram-2-anatomy.png)

At the top is YAML frontmatter, between two `---` delimiters. This is the machine-readable layer. Color hex codes, typography sizes, spacing scale, component tokens. Agents and tools parse this as structured data.

Below the frontmatter is the markdown body. This is the human-readable layer. Section headings for visual theme, color roles, typography rules, layout principles, components, do's and don'ts. Each section is prose that explains why the values exist and when to deviate.

The format is intentional. A pure JSON token file gives the agent values without intent. The agent knows `primary` is `#635bff` but does not know that you reserve that color for trust signals and never use it decoratively. A pure markdown design guide gives the agent prose without precision. It knows the brand feels precise but does not know whether precise means 7px or 8px spacing.

DESIGN.md gives the agent both. Tokens for what, prose for why. The official spec defines eight ordered sections: Overview, Colors, Typography, Layout, Elevation, Shapes, Components, Do's and Don'ts. Each section can be omitted, but the ones present must appear in spec order.

The Google Labs repo at `github.com/google-labs-code/design.md` holds the spec, currently at version `alpha`. VoltAgent's `awesome-design-md` repo holds the community collection of brand systems extracted from public CSS. A second collection at `getdesign.md` and the design tool at `designmd.app` round out the ecosystem. None of these are dependencies. DESIGN.md is a file. Tools read it. The file is the protocol.

## Visual proof: same prompt, three contexts

The clearest demonstration of what DESIGN.md actually does is to show the same prompt processed by the same model under three different design contexts.

The prompt: "Design a login page for a SaaS product. Email and password fields, primary action button, secondary link below."

**Without DESIGN.md.** Generic AI-default styling. Tailwind beige.

![Generic AI-generated login page mockup, white background with blue button and default styling, no brand identity](ui-generic.png)

The output works. It is also indistinguishable from every other AI-generated login page on the internet. White background. Blue button. Gray inputs. System font. Border-radius 4px. This is what the agent picks when it has no design context. It is not wrong. It is just nobody's brand.

**With a Stripe-flavored DESIGN.md.** Precision fintech.

![Stripe-style login page mockup with blurple primary button, light-weight headline typography, 8px grid spacing, blue-tinted shadow on the card](ui-stripe-style.png)

The button is blurple, `#635bff`. The headline is a light-weight sans-serif at a larger size. The card has a subtle blue-tinted shadow rather than a generic neutral one. The corner radius is 8px, not 4px. The spacing follows an 8px grid. The same component, the same model, a recognizable visual identity that did not exist in the prompt.

**With a Linear-flavored DESIGN.md.** Minimalist developer tool.

![Linear-style login page mockup, dark mode background, condensed typography, single violet accent, tight spacing with minimal shadows](ui-linear-style.png)

Dark mode background. Condensed typography. Almost no shadows. A single violet accent. Tight 4px spacing. Different brand, same component, recognizable identity.

Three pages, same prompt, same model, three completely different visual outcomes. The variable is the DESIGN.md context, not the model.

This is the proof. The model is not bad at design. The model has no persistent reference for what your design looks like. Give it one, and the output stays consistent. Do not, and it generates a fresh guess every time.

## The minimum viable DESIGN.md

Most coverage walks through the full nine-section spec. Most teams should not start there. The nine-section version is the destination, not the starting point.

The minimum viable DESIGN.md has five sections. Each section exists because without it, the agent produces a specific predictable failure.

**1. Visual theme and atmosphere.** Two sentences describing the feel. Not the values. "Technical and luxurious, precise and warm." "Editorial and confident, never decorative." The agent uses this as a north star when it has to make a judgment call between two acceptable options.

**2. Colors with roles.** Not just hex codes. Each color gets a job description. `primary: "#635bff" - for primary actions and trust signals, never decorative`. `error: "#ea2261" - for failure states only, never for emphasis`. Color roles kill the most common failure mode, where the agent uses your accent color decoratively because it picks one acceptable color for each element without a system.

**3. Typography.** Font family, weight, size scale, line heights. Spec the headline weight explicitly. Specify which weights are off-limits. Most AI-generated typography fails because the agent reaches for the most common variant, which is often not yours.

**4. Components.** At minimum, button variants and card specs. Border-radius, shadow, hover state, disabled state, loading state. The agent has no idea what your buttons look like unless you tell it.

**5. Do's and don'ts.** Five rules, no more. "Never use border-radius above 8px." "Never use pill-shaped buttons." "Never use heavy font weights for headlines." This is the section that prevents the most subtle drift, because the agent will always reach for plausible defaults and your specific identity often violates them.

The five-section version covers the highest-impact failure modes. Add Layout, Elevation, Responsive, and Agent Prompt Guide as you hit inconsistencies. A partial DESIGN.md that ships is better than a complete one that does not.

For ready-made starters, `github.com/VoltAgent/awesome-design-md` has 423 brand systems. Browse it, find a brand whose aesthetic is close to yours, and edit from there. Do not start from a blank file unless you enjoy the activation energy problem.

## The token cost reality

This is the section nobody talks about, and it matters once your project scales.

A full DESIGN.md consumes roughly 30,000 tokens per agent query. That is context window space your agent cannot use for code reasoning. JSON design tokens alone carry the same value content in about 80% fewer tokens, but they lose the intent layer that makes markdown effective.

For a small project with one or two contributors and short sessions, 30,000 tokens is not a meaningful cost. For a large project with long sessions, multiple files in context, and per-token agent pricing, it is.

The practical guidance is to trim to the five-section minimum and keep the extended sections as a reference doc the agent loads on demand. You can also split your DESIGN.md into two files: a compact `DESIGN.md` in the project root that the agent reads on every session, and a `DESIGN-extended.md` that holds the full nine-section content and lives in `/docs/`. The agent reads the compact version for routine work and the extended version for deeper UI questions.

The AGENTS.md research from late 2025 is relevant here. The paper found that human-written AGENTS.md files improved task completion by 4%, LLM-generated ones hurt by 2%, and all of them added 20% or more to inference cost. Treat DESIGN.md the same way. The cost is real. The value depends entirely on how sharp your file is. A loose file imposes the token cost without the consistency benefit. Tight files pay back.

## The CLI tooling nobody mentions

Google shipped a CLI alongside the spec. Most introductions skip it. It is one of the strongest reasons to take the format seriously.

```bash
npx @google/design.md lint DESIGN.md
```

The `lint` command validates structure, checks token references, detects orphaned tokens, validates section order, and runs WCAG AA contrast checks on every color combination in your file. The exit code is non-zero on errors. Add it to CI.

```bash
npx @google/design.md diff old.md new.md
```

The `diff` command reports token-level changes between two versions. Useful when reviewing PRs that modify the design system.

```bash
npx @google/design.md export DESIGN.md --format tailwind
```

The `export` command converts tokens to Tailwind config, W3C DTCG format, or raw JSON. This is the bridge between your DESIGN.md and your existing styling infrastructure.

The WCAG contrast checks are the underrated feature. Most teams have an accessibility regression in their UI somewhere. The lint command catches contrast failures at write time, before a single component is generated. For organizations with accessibility requirements, this alone is worth the adoption.

## Where DESIGN.md still breaks

The introductions do not cover this section honestly. The format is useful and incomplete. Four places it breaks.

**The spec is alpha.** Google flags this explicitly. The token schema is under active development. Animation tokens are not specified. Dark mode tokens are not formalized. Responsive breakpoints are loosely defined. If you adopt now, expect to migrate when the schema stabilizes. The migration will probably be mechanical, but it is not free.

**Extracted DESIGN.md goes stale.** When you grab a Stripe DESIGN.md from VoltAgent's collection, you are getting a snapshot of Stripe's public CSS as of the extraction date. Stripe ships redesigns. Your DESIGN.md does not auto-update. Within six months, your file may diverge from the actual brand it claims to represent. For your own brand, the file goes stale when your team ships visual changes without updating the file. Design system teams have always managed this lag. DESIGN.md does not solve it, it just relocates it.

**There is no runtime enforcement.** DESIGN.md is guidance, not a linter. The agent reads the file, tries to follow it, and produces something close. Nothing stops the agent from outputting `border-radius: 16px` when your do's-and-don'ts forbid radii above 8px. If you need hard enforcement, you still need CSS linting rules, a design review step, or a component library that constrains by construction.

**Team coordination is unsolved.** One developer maintaining a DESIGN.md is easy. Twenty developers across a Figma-first design team is hard. Most design teams work in Figma, not in markdown files. The two-source-of-truth problem is real. Until there is solid tooling to keep DESIGN.md and Figma in sync, large teams will face friction. Plugins are emerging for this. None are great yet.

One more caveat worth naming: 73,000 GitHub stars is a signal of resonance, not proof of efficacy. There are anecdotal reports of "off-brand generation rates halving" but no controlled study yet. I would treat the file as high-probability useful, not as settled science.

## A 30-day adoption path

If you are reading this and want to start, here is the four-week sequence that has worked for the teams I have advised.

**Week 1: Adopt one from the collection.** Browse VoltAgent's repo, find a brand whose aesthetic is close to where you want to go, and drop the DESIGN.md into your project root next to your AGENTS.md or CLAUDE.md. Spend the week generating UI components with your agent and noting where the output now feels more consistent. Do not customize yet. Observe what the file does on its own.

**Week 2: Write your minimum viable version.** Use the five sections from earlier in this article. Theme. Colors with roles. Typography. Components. Do's and don'ts. Replace the brand-flavored DESIGN.md from week one with your own. Use the lint command. Fix every warning. Use the agent to generate the same UI components from week one and watch what changes.

**Week 3: Add to CI and set up the export pipeline.** Wire `npx @google/design.md lint` into your CI so the file cannot drift unnoticed. If you use Tailwind or design tokens elsewhere, run the export command and merge the output into your config. Now your DESIGN.md is the single source for both your AI agent and your styling infrastructure.

**Week 4: Extend and share.** Add the remaining sections from the spec as you hit inconsistencies (Layout, Elevation, Responsive, Agent Prompt Guide). Share the file with one other engineer on your team. Document one specific improvement (a component that used to drift and now does not) so you have evidence when you propose it to the rest of the team.

By the end of week four, you have a working DESIGN.md, CI integration, and a concrete data point. That is the foundation. Everything after is iteration.

## Where this is going

The instruction-file family is the new persistence layer for AI-assisted development. AGENTS.md fixed behavioral consistency. SKILL.md fixed task-specific expertise. DESIGN.md fixes visual consistency. These three files now do for AI development what readme files, code conventions, and component libraries do for human development. They are the persistent context that survives across sessions.

The next file will arrive. There are credible bets on `TEST.md` for testing conventions, `DEPLOY.md` for release expectations, `OBSERVE.md` for monitoring and alerting context. The pattern is settled. Plain markdown, structured prose, machine-readable values where useful, human-readable rationale where needed, in the project root where every agent can find it.

The bigger thing happening underneath: the leverage is moving from model capability to file quality. The agents get better-instructed rather than dramatically smarter, and that compounds for the teams that figure it out first.

Google open-sourcing DESIGN.md is the signal that this layer is becoming a standard, not just a Google thing. The spec is still alpha. The format is not yet finished. Adopt anyway. The cost is low, the operational benefit is real within a week, and the alternative is watching your AI-generated UI keep looking like everyone else's.

If you want a starter, browse `github.com/VoltAgent/awesome-design-md`, pick a brand, drop the file, and generate a page. The difference shows up on the first render. After that, you are iterating on a file, not arguing with a model.
