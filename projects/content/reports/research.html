spec.md and the Spec-Destination Debate

Research brief, 2026-05-21. What practitioners actually say about where the spec should live, and how strong the case is for Notion (and similar).

Existing piece note. The May 18 article (/Users/marcokotrotsos/PERSONAL/Content/drafts/spec-driven-belongs-on-the-board/draft.md) made this argument with Linear as the canonical example. This research surfaces a stronger, more specific case for Notion in particular, plus a meaningful dissent worth steel-manning. Treat as material for an expanded V2 of the piece, a Notion-specific deep-dive, or a "the debate moved" follow-up.
The short version. The community has converged on three positions. Position A: keep the spec in a markdown file in the repo, version-controlled, close to code (this is the default everyone landed on first). Position B: the spec belongs in a workspace tool like Notion or Linear, with markdown as the export format. Position C: spec-driven development itself is the wrong move, more Waterfall than agile. Notion's May 13 Developer Platform launch was the loudest argument yet for Position B, with explicit positioning as "any data, any tool, any agent" and direct MCP integration with Claude Code, Cursor, Codex, and Decagon. The strongest dissent comes from Marmelab's "Waterfall strikes back" piece, which deserves to be answered honestly in any article making the Notion case.

How the discourse breaks down

Position A: spec.md belongs in the repo

GitHub Spec Kit AWS Kiro Claude Code official best practices Tessl BMAD SuperClaude HumanLayer CLAUDE.md guidance

This is the dominant pattern in the AI-engineering community right now. The spec lives in a folder in the repo (often specs/ or .specify/), version-controlled, sitting next to the code it describes. The argument is consistency, portability, and locality: the spec travels with the codebase, gets reviewed with the code, gets versioned with the code.

The mainstream argument

"The spec is versioned alongside the code (often in a specs/ or .specify/ directory in the same repo). The spec is the source of truth. When a bug or feature request comes in, the spec is updated first; the code is regenerated or modified to match." (Augment Code, Product Builder, BCMS guides 2026)

Anthropic's own Claude Code best practices recommend: write a complete spec to SPEC.md, then start a fresh session to execute it. The new session has clean context focused entirely on implementation and a written spec to reference.

Strongest defenders of this position

  • GitHub Spec Kit: four-phase structured process, integrates with 30+ coding agents, treats markdown specs as first-class artifacts
  • AWS Kiro: agentic IDE that plans and builds directly from written specifications
  • Tessl: launched a spec-driven framework and registry
  • Anthropic Claude Code docs: explicit guidance to use SPEC.md in the repo
  • HumanLayer: "Writing a good CLAUDE.md" - sustained advocacy for keeping AI instruction files alongside code

Position B: the spec belongs in a workspace tool, files are the export

Notion (May 13 launch) Linear MCP advocates Pavanbelagatti (DEV: MCP workflow) Marco's May 18 article

This position argues that a spec has lifecycle, ownership, status, and dependencies that a flat file is bad at. The board (or workspace) holds the spec. The file is the snapshot the agent reads.

The strongest single piece of evidence

Notion's May 13, 2026 Developer Platform launch. CEO Ivan Zhao stated: "use your Notion database as a sheer canvas to power both your workflows and your agents." The platform pitch is "Any data, any tool, any agent." Notion now supports Claude Code, Cursor, Codex, and Decagon as external agent integrations. It also launched Workers (cloud-sandboxed code execution inside Notion) and Database Sync (live external data from Salesforce, Zendesk, Postgres).

Notion's own framing from their docs: "Notion has evolved into the source of truth for teams' product specs, project plans, runbooks, and institutional knowledge."

Notion MCP gives "AI tools secure access to your Notion workspace, designed to work seamlessly with popular AI assistants like Claude Code, Cursor, VS Code, ChatGPT, and more."

The mechanism that makes this practical

Notion MCP and Linear MCP both exist and are production-ready as of May 2026. The integration problem that originally forced specs into files (agents read markdown, agents could not talk to Notion/Linear) is gone. Notion's MCP server is hosted, supports the major coding agents, and "updates are instantly reflected without re-indexing or retraining."

Notion's specific product surface for this

  • notion.com/use-case/engineering-tech-spec: a dedicated landing page for tech specs in Notion, with templates and integrations.
  • Custom Agents (Notion 3.0, September 2025; Notion 3.3, February 2026): over 1 million built by customers; AI teammates handling repetitive tasks; now enhanced with external data and custom logic.
  • Workers: deploy custom code without external infrastructure. Free through August 2026.
  • External Agent Integration: chat with and assign work to external agents (Claude Code, Cursor, Codex, Decagon) alongside Notion's own.

Position B-prime: the nuanced version Notion itself practices

Worth flagging

Ryan Nystrom (Notion engineer) wrote about Notion's internal AI engineering workflow on Lenny's Newsletter. The piece describes spec-first development as "writing and checking agent specs into the repo." Their Boxy system lets engineers @mention Codex from within Notion comments to get a full pull request with screenshots in 20 minutes.

The practical pattern at Notion itself appears to be: both. Notion is the discussion and triage layer. Spec gets refined there. The final agent-readable spec ends up committed to the repo as a markdown file. The agent reads from the file, but the conversation and lifecycle live in Notion.

This complicates the "kill spec.md" framing. The honest version is: the file is fine as the snapshot agents work against. The error is treating the file as the system of record.

Position C: spec-driven development is wrong

Marmelab "Natural Language Development" advocates

The strongest dissent comes from Marmelab's "Spec-Driven Development: The Waterfall Strikes Back" (November 2025). Marmelab frames SDD as a step in the wrong direction, comparing it to discredited Waterfall methodology.

The dissent

"Software development is fundamentally a non-deterministic process. Big design up front has proven to fail most of the time."

Seven specific problems Marmelab identifies:

  1. Context Blindness: agents miss existing functions despite text search
  2. Markdown Overload: developers spend excessive time reading verbose design documents
  3. Bureaucratic Excess: the three-step process generates repetition and unnecessary complexity
  4. Terminology Misuse: generated "user stories" often misrepresent actual user needs
  5. Double Review Burden: code requires review both in spec and final implementation phases
  6. Unreliable Compliance: agents do not reliably follow specifications
  7. Diminishing Returns: SDD becomes unusable as codebases grow

The counter-proposal: iterative "Natural Language Development" with simple, conversational instructions logged in version control. No big spec up front.

This dissent is worth steel-manning in any article making the Notion case. The honest read of the Marmelab piece: it is not really attacking where the spec lives. It is attacking the whole upfront-spec premise. If you accept spec-driven development as worthwhile (which Marco's earlier piece argued strongly), Marmelab's critique still leaves you with the question Marco's piece tried to answer: where should the spec live? The Marmelab piece does not address that, because for Marmelab, the answer is "nowhere, do not write big specs."

The Notion vs Linear comparison (the practical question)

If Position B is right, the next question is whether Notion or Linear (or Jira, or Asana, or Coda) is the better destination. The 2026 comparison landscape:

DimensionNotionLinear
Spec depth (long-form, structured docs)Strong (designed for it)Light (issue descriptions can be long but not built for it)
Lifecycle / kanban / issue managementPossible but not nativeStrong (designed for it)
MCP integrationHosted, multi-agent, May 2026 platform launchMature, in production with Claude Code and others
Custom Agents / Workers in the workspaceYes (Notion 3.3 + Workers)No (no native agent platform)
Native database for non-spec dataYesNo (issues only)
Cost ceiling for AI featuresHidden behind tiers, AI usage often a paid add-onLower complexity, narrower scope

The intuition that emerges from the practitioner discourse: Notion is the better destination if the spec has substance (long-form requirements, multiple stakeholders, evolving discussion). Linear is the better destination if the spec lives primarily as a work item with a lifecycle. Many real-world setups use both: spec discussion and refinement in Notion, work tracking in Linear, with the MCP layer letting the agent read from either.

What is missing from the discourse

Three gaps the article could fill:

  • A clean diagram of the round-trip. Notion (or Linear) holds the spec. Agent exports markdown when needed. Updates flow back. Nobody has drawn this clearly with the May 2026 MCP integrations as the wire.
  • A decision tree for Notion vs Linear vs both. The discourse is tribal. A practitioner-grade decision framework is missing.
  • A response to Marmelab. The Waterfall-strikes-back critique is unanswered in the pro-spec-driven community. The honest answer is that lightweight specs in Notion (or Linear) with agent execution are not Waterfall, because the spec evolves continuously with the work. This needs to be said.
