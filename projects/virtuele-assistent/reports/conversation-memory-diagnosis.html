Virtuele Assistent · diagnosis
Diagnosis and fix plan

Why the assistant hallucinates after a few turns

The conversation history reaching the model decays into placeholders after the first turn or two. This is what causes the drift, and it is fixable.

In one paragraph

On each request the whole conversation is flattened into a single text blob and sent to the model as one user message. Worse, within that blob the earlier assistant answers are not the real text, they are replaced by trace-id placeholders like TRACE:79e4b651.... Only the most recent answer keeps its text. So after a few turns the model can no longer see what it told the user earlier, loses the thread, and answers off-topic. Retrieval makes it worse because it only ever sees the latest user message, with no conversation context. The fix is to send real, structured turns to the model and to rewrite follow-up questions into standalone queries before retrieval.

The symptom

The assistant answers well on the first question, then gets less reliable as the conversation continues. Follow-up questions that depend on earlier turns ("and for my child?", "is consent needed?") get vague, wrong, or off-topic answers. It looks like the model "forgets" what was just discussed.

The whole thing is one user message. The question is about consent for a child's passport, but the turn that established "a child's passport" is now just TRACE:7463fc53.... The model cannot see it, so it answers off-topic. The judge scored this answer answer_relevance = 0.

Why it happens: two stacked problems

Problem 1 — the conversation structure is lost Confirmed

The history is concatenated into one user message with user: / assistant: / tool: text prefixes, instead of being sent as real user and assistant turns. The model cannot cleanly tell apart what the user said, what it answered before, and what was retrieved. Models are trained on structured turns, not a transcript pasted into one message. Source: buildLLMQuery plus the <String, String> agent input type.

Problem 2 — earlier answers decay into trace-id placeholders 9 of 11 multi-turn traces

This is the main cause. In the history sent back to the model, older assistant answers are replaced by a marker like ​TRACE:<id>​. Only the most recent answer keeps its real text. So the model's memory of the conversation rots after a turn or two. The answer text is generated in full (the trace output shows it), so this is a history persistence and replay problem, most likely in the frontend message store combined with a trace marker the stream appends. The backend then flattens whatever it receives. Empty assistant: and tool: lines from prior tool-calling steps are also flattened in as noise.

Problem 3 — retrieval is starved of context Confirmed

HyDE and vector search only ever see the latest user message (OriginalQueryContext(lastUserMessage)), with no conversation. On a follow-up like "en wat kost dat?" the query is underspecified. HyDE then writes a hypothetical document from that vague query and embeds it, so retrieval can be steered toward the wrong pages with confidence. There is no step that rewrites a follow-up into a standalone question.

Why it gets worse specifically after a few turns

On turn 1 there is no prior context to lose, so the answer is good. On turn 2 the single prior answer is still recent, so it is usually intact. By turn 3 or 4 the earliest turns have decayed into TRACE:<id> placeholders, and the question increasingly refers back to them. So the grounding the model needs is exactly the part that has been deleted. "Hallucinates after a few turns" is literally the history rotting into trace ids after a few turns.

The solid evidence is the concrete multi-turn traces above, not that percentage.

Separately, each turn is recorded as its own trace and conversations are not grouped into a single session in Langfuse. That does not cause the hallucination, but it makes multi-turn debugging harder and is worth fixing.

What we can do

Priority 1 Stop sending trace-id placeholders as assistant history

Preserve the actual assistant answer text for every prior turn, and strip the ​TRACE:...​ markers before the history reaches the model. This is the highest-impact and most concrete fix. With the real prior answers restored, the model can follow the thread again and most multi-turn hallucinations should drop.

Where to look: the frontend message store in agent-frontend (how assistant messages are saved and replayed), and wherever the TRACE: marker is appended to the stream. The backend should also strip these markers defensively.

Priority 2 Send structured turns to the model, not a flattened blob

Pass the IncomingMessage list to the agent as real user and assistant messages instead of joining them into one string. The data already exists at the boundary, it is discarded one layer before the model. Koog supports a prompt built from multiple turns; the strategy input type would change from String to a richer type, or the prompt would be seeded with the history before run.

Where: buildLLMQuery / agent.run in ChatHttpRoute.kt, and the strategy type in AgentStrategy.kt.

Priority 3 Rewrite follow-up questions into standalone queries before retrieval

Add a step that condenses the conversation plus the latest message into one complete, self-contained question, then run HyDE and search on that. This fixes the context starvation and makes HyDE on-topic again on follow-ups. It is the standard fix for multi-turn RAG.

Where: before the RAG tools run; feed the rewritten question into OriginalQueryContext.

Also worth doing Guards and hygiene
  • Gate the answer on retrieval quality. You already compute rag_top_score. When it is low, have the assistant say it cannot find the answer and offer contact, instead of answering from thin context.
  • Bound the history sent per turn (last N turns or a token budget) so older turns stop diluting attention once their real text is restored.
  • Fix session grouping in Langfuse so a conversation is one session, which makes multi-turn debugging far easier.

What is still open

I have not yet pinpointed where the TRACE:<id> marker is injected and why older assistant texts are dropped on replay. The answer is generated in full, so the loss happens in storage or replay, most likely in the agent-frontend assistant-ui message handling. Confirming that is the next concrete step before writing the Priority 1 fix.
