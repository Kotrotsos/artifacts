Change description

Per-tenant system-prompt template switch

A single tenant can be moved onto a different system-prompt template (the refactored refactor/system-prompt-main) from the admin, without changing the default for everyone else.

In one paragraph

The backend used to fetch one hardcoded template (generic_system_prompt_v3) for every tenant. Now each tenant can carry an optional systemPromptTemplate override, set from the admin. If set (and on the allow-list), the assembler fetches that template first and falls back to v3 if anything goes wrong. The default is unchanged, so this is safe to merge: nothing changes until a tenant is explicitly switched. A latent bug was also fixed: slash-namespaced prompt names (like refactor/system-prompt-main) were unfetchable because the name was not fully URL-encoded.

Fail-safe

The override is only honoured if the name is on the SELECTABLE_TEMPLATES allow-list, and the chosen template is tried first with the standard chain (v3 → v2) still behind it. A missing, mistyped, or unreachable template can never break assembly — it silently falls back to v3. This was confirmed during testing.

How it's wired in Langfuse

Templates live in Langfuse as managed prompts. The app fetches them by name at request time (cached 5 min). Nothing about prompt storage changed; only which name the backend asks for.

prompt generic_system_prompt_v3
labels: latest, production · the default for all tenants
+
prompt refactor/system-prompt-main
labels: latest, production · opt-in per tenant

Two Langfuse details that matter

1. Slash in the name. refactor/system-prompt-main contains a /. The app now URL-encodes the full name as one path segment (encodeURLPathPart), so the fetch resolves. Before this fix, the whole refactor/ namespace was unfetchable (404) and silently fell back to v3.

2. No test label. refactor/system-prompt-main is on latest + production only. In dev/staging the app requests the test label and falls back to production, so it resolves — but an edit made only on latest will not appear until it is also promoted to production.

The variable contract the new template adds

refactor/system-prompt-main uses 5 vars the old contract didn't expose:

  {{bot_name}}           ← appName (or orgName if unnamed)     [mapping only]
  {{email}}              ← vars.email                          [mapping only]
  {{org_short}}          ← "de gemeente" / orgName             [derived]
  {{taalniveau}}         ← new field, default "B1" (B1 / A2)   [new field]
  {{extra_topic_rules}}  ← new field, optional per-tenant text [new field]

Rollout

Safe to merge to test

Default unchanged — every tenant stays on v3 until switched in admin. Flip one tenant, validate with the preview button, publish, then move to the next.

Do this before switching a live tenant

Run an eval (answer_relevance_v2 / the groundedness evaluator) on the refactor prompt versus v3 for that tenant before exposing it to real traffic. The render being clean does not prove the prompt answers better.
