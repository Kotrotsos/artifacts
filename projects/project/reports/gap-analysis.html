How Marco works

Marco builds the same idea over and over, never resumes, and never ships the good version.

The folder tree reads like a workbench, not a portfolio. He is a fast, prolific prototyper who reaches for a fresh directory every time an idea returns instead of reopening the prior attempt. The pattern is consistent across every cluster:

  • New folder, not new branch. When a concept comes back, he scaffolds again from zero. The same coding agent is rebuilt 5 times under archer*; the same note app 6 times under notee/noti/zen-notee; the same random-string CLI 4 times under randy*.
  • The mature version is rarely the deployed one. The most invested apps (aside, notee-desktop, promptlan) have no deploy config, while the abandoned or throwaway ones got Docker and Railway. Polish and shipping are decoupled.
  • Client work repeats the same wiring by hand. Next.js front end + Python ML back end + Azure/EntraID auth is re-plumbed per engagement (nha-sa, bsr, complia, klafs) with no shared scaffold.
  • Git is inconsistent. 108 of 182 folders have no repo. Active creative and security work (osint, iam, dot2dot, nonomaker, worldbuilder) has no history, so rebuilds cannot even be diffed against the prior attempt.
  • Secrets leak. Live Railway Postgres creds in ai insights, a hardcoded Keesing JWT in nonomaker/notes.txt, loose cert.pem/key.pem in inboxinsights.

The throughline is not a technology gap. It is a memory gap. There is no catalog of what already exists, so prior work is invisible at the moment a new idea strikes, and the cheapest move is always to start over.

What is missing

Across all six clusters the recurring true gaps rank as follows: (1) no master index of projects, (2) no shared libraries so the same tool code is copy-pasted, (3) no secrets discipline, (4) no consistent deploy convention, (5) no ML/eval/observability sink. Every downstream gap is enabled by the first one. You cannot build a shared agent-core, dedup the rebuilds, or enforce secrets hygiene if you do not first know what the 182 folders contain.

Why Project Atlas wins

Atlas is the root-cause fix; every other candidate is a leaf. The duplication, the dead 102 GB, the orphaned best-versions, the leaked secrets — all of them exist because there is no answer to "what do I already have?" at the moment work starts.

  • It is upstream of the other four. agent-core, the secrets sweeper, and the deploy abstraction all need to know which projects exist and which are alive. Atlas produces that input. Build it first and the others get cheaper.
  • It pays back immediately. 108 ungit'd folders and 102 GB with 20 GB+ stale means the first run reclaims disk and surfaces kill/merge candidates the same day.
  • It is small and self-contained. A local read-only scanner over one directory. No auth, no deploy target, no client dependency. Marco can finish it in a sitting, which matters given the shipping pattern.
  • It directly attacks the behavior. The reason the 5th archer and 6th notee got built is that prior work was invisible. A queryable index, checked before mkdir, breaks the new-folder reflex.

The secrets leak is real and urgent, but it is one finding Atlas can surface as a flag rather than a separate product. Atlas first, then act on what it reveals.

What to build now

A single local CLI, atlas, that walks /Users/marcokotrotsos/projects and writes both a machine-readable atlas.json and a static atlas.html dashboard. Per folder it records: name, path, size, last-modified, primary language, git presence and last-commit date, remote URL, and deploy signals (Dockerfile, railway/vercel/azure config). It then groups by name-stem and code similarity to surface duplicate clusters, classifies each project as ship merge or kill using last-touched, git, deploy state and cluster membership, and prints a dedup map plus a secrets-leak flag. Re-runnable so the catalog stays current.
