What service_role grants

In a self-hosted Supabase stack, service_role is the privilege tier that bypasses every Row Level Security policy and connects to PostgREST as the equivalent of a database-superuser-scoped role. With one bearer token the holder can:

  • Read every row of every table, including guardian_*, consent_records, explorer_profiles, and the auth schema.
  • Insert, update, delete arbitrary rows.
  • Call RPC functions, including ones that wrap privileged operations.
  • Hit GoTrue admin endpoints to enumerate users, reset passwords, mint impersonation links.
  • Hit Storage to read or delete any object in any bucket regardless of bucket policy.

Step-by-step practical exploit

  1. Pull the credential. One anonymous HTTP GET to /api/platform/projects/default/settings on supabase.unomundi.com. No credentials needed, no rate limit observed on the rescan.
  2. Resolve a reachable data plane. Two paths exist today. The public one is https://dev-supabase.unomundi.com/rest/v1/, confirmed reachable from the public internet (HTTP 200, returns the full OpenAPI schema). The nginx Basic Auth rule covers Studio UI paths only; /rest/v1 is not gated. The internal Kong at 100.52.182.111:8000 is VPC-internal and would need a pivot, which is unnecessary given the public path.
  3. Send authenticated requests with the leaked token. Against any PostgREST endpoint on dev-supabase: 
    GET https://dev-supabase.unomundi.com/rest/v1/<table>
apikey:        <leaked service_role JWT>
Authorization: Bearer <leaked service_role JWT>
    PostgREST verifies the HS256 signature against jwt_secret, reads role: service_role from the payload, switches the Postgres session role, and bypasses every RLS policy on the queried relation.
  4. Pivot. The same token authorises GoTrue admin endpoints and Storage. From a single anonymous GET the attacker reaches full read-write on every GDPR-K relevant table on a children's app, plus the ability to impersonate any user.
Important: rotating the two pre-minted JWTs is not sufficient on its own. If the operator rotates the tokens but does not remove the unauthenticated /api/platform/projects/default/settings endpoint, an attacker simply re-reads the new jwt_secret from the same response and mints a fresh service_role JWT locally with a 10-year expiry. The endpoint itself must stop being publicly reachable.

F-3 evidence, admin still points at dev backend

The bundle served at admin.unomundi.com/assets/index-LVG8KGiM.js is 1,476,471 bytes, dated 2026-04-27, still the active script referenced from index.html. It contains exactly one production Supabase URL:

$ grep -oE 'https://[a-z0-9.-]+\.unomundi\.com' index-LVG8KGiM.js | sort -u
https://dev-supabase.unomundi.com

Build-time env literals visible in the bundle: VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY, VITE_BACKEND_URL. There is no prod-only Supabase host. Admins logging in at admin.unomundi.com are talking to the dev backend, whose data API is publicly reachable, whose Basic Auth covers Studio UI only, and whose JWTs are the ones leaked on the prod host.

Recommendations, ordered by blast radius

  1. Rotate jwt_secret and re-mint both JWTs immediately. Treat the 2026-03-03 keypair as fully burned. Any integration holding the old anon key needs updating as part of rotation.
  2. Remove public reachability of supabase.unomundi.com and dev-supabase.unomundi.com. Self-hosted Studio is a management plane; it belongs behind a VPN, SSO, or IP allowlist, not a public hostname. The current Basic Auth is a single shared password protecting a privileged surface and does not cover /rest/v1/.
  3. Repoint admin.unomundi.com at a real production Supabase project, with separate JWT keys and an isolated database. Rebuild the admin SPA with a prod-only VITE_SUPABASE_URL.
  4. Audit /api/platform/* exposure on both Supabase hosts. The Next.js Studio app ships a platform API that returns infrastructure secrets when it believes it is running on localhost. It must not be reachable unauthenticated.
  5. Database and Storage log review for 2026-03-03 onward. With a 4-year-old service_role JWT and an unauthenticated leak path, prior abuse is plausible and must be checked. Pull pg_stat_statements, GoTrue audit logs, and Storage access logs for anomalies, in particular reads of guardian_* or consent_records from non-application source IPs.
  6. GDPR Art. 33 clock. If the log review surfaces evidence of unauthorised access to children's PII, the 72h notification to the AP (Autoriteit Persoonsgegevens) applies. Coordinate with the DPO before the window closes.
  7. Remove or auth-gate api.unomundi.com/docs (Scalar API reference), unless intentional for the public.

Methodology and limits

This rescan used anonymous HTTP HEAD and GET requests against documented Supabase Studio platform endpoints and against the admin SPA. No authenticated requests were made. No SQL was executed. No user records were read. No data was exfiltrated beyond the management-plane responses cited above. The leaked JWTs were not used against any endpoint.

Structural proof in this report is sufficient to characterise remediation state. Further proof would require crossing into active exploitation, which is out of scope.
