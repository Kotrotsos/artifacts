Red Team Assessment

Security Assessment of capibara, a request-capture service

An owner-authorized passive and active red-team of the live application: reconnaissance, client-side reverse engineering, access-control and authorization testing, injection and forgery testing, and abuse-resistance checks. Testing was non-destructive: no denial-of-service, no mass fuzzing, no data destruction.

Target capibara-production-c978.up.railway.app Entry /jomlat7cik49 Date 4 June 2026 Method Passive + active, non-destructive Stack Node/Express on Railway

01Executive summary

capibara is a webhook and request-inspection tool: any path /{hash} becomes a capture bin, requests sent to it are recorded in full, and the owner reads them back at /{hash}/read after entering a one-time secret token. The application is well engineered from a security standpoint. The classic failure modes for this kind of tool, stored XSS in the request viewer and cross-tenant data access, are both correctly handled. No critical or high-severity issue was found.

The remaining findings are about abuse resistance and defense in depth, not broken authentication or injection. The two that matter most: there is no rate limiting or resource ceiling anywhere (an availability and enumeration concern), and the bin model lets the first visitor of a name claim its read token, which allows silent squatting of predictable names. Both are fixable without redesign.

Priorities

  1. Add rate limiting and resource caps (requests per bin, bins per IP, request rate, body size, retention TTL). (M1)
  2. Close the bin-squatting gap: bind a bin to its creator, or warn clearly when a name already exists. (M2)
  3. Send security headers (CSP, X-Frame-Options, nosniff) on the pages that render captured data. (M3)
  4. Remove the existence oracle and lock down CORS. (L1, L2)

04Medium findings

M1No rate limiting or resource ceilingsMedium

What we found

Twelve rapid wrong-token requests to /{hash}/requests all returned 401 with no 429 and no backoff. There is no observable limit on request rate, on the number of requests stored per bin, on the number of bins that can be created, or on retention. The store appears to be in-memory (no database was observed, responses are immediate, and the design is single-tenant per Railway service).

Why it matters

  • Memory exhaustion / DoS. An attacker can flood one bin with requests, or create unbounded bins, until the process runs out of memory and Railway restarts it, dropping every other user's captures.
  • Frictionless enumeration. No rate limit means the existence oracle (L1) and any future guessable secret can be probed at full speed.

Recommendation

Add per-IP rate limiting (for example via express-rate-limit behind Railway's proxy, trusting X-Forwarded-For correctly), plus hard caps: max stored requests per bin (ring-buffer eviction), max bins per IP per hour, a max captured-body size (truncation already exists, enforce a global byte budget), and a retention TTL that evicts idle bins. This also bounds the in-memory store.

M2Bin-name squatting via the first-touch token modelMedium

What we found

A bin's read token is generated and shown exactly once, to whoever first navigates to that name in a browser. The site actively encourages human-readable names ("just navigate to /anything-you-like", plus a custom-name box). Anyone can pre-create predictable names (/stripe, /github, /test, /webhook-prod, a company or product name) and quietly retain their tokens.

Why it matters

If a victim later picks a name an attacker already owns, the victim is shown a bin page with no token (only a non-zero request counter as a subtle tell) while the attacker holds the working read token. Every request the victim then points at that bin, often containing webhook payloads, bearer tokens, signing secrets, is silently readable by the attacker. We verified that captured Authorization: Bearer headers are stored and returned verbatim to the token holder.

Recommendation

Bind a bin to its creator: set a signed creator cookie at creation and only reveal the token (and allow reads) to that identity, or scope the token to a session. At minimum, when a requested name already exists, show a clear "this bin already exists and is controlled by whoever created it, choose a fresh random name" warning, and prefer server-issued random names over user-chosen ones for anything sensitive.

M3No security headers on pages that render captured dataMedium

What we found

The bin page and the /read viewer return only cache-control: no-store. There is no Content-Security-Policy, no X-Frame-Options or frame-ancestors, no X-Content-Type-Options: nosniff, and no Referrer-Policy. These are the pages that render attacker-influenced captured content.

Why it matters

The viewer's escaping is correct today, so there is no XSS now. But a request inspector renders hostile input by definition, so a CSP is the safety net: if any future change introduces an unescaped sink, a strict CSP turns a full account-equivalent compromise (the token lives in localStorage) into a blocked event. The missing X-Frame-Options also allows the reader to be framed for clickjacking.

Recommendation

Send on all app responses: Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; frame-ancestors 'none'; base-uri 'none' (move the small inline theme bootstrap to a nonce or into the existing JS file), plus X-Frame-Options: DENY, X-Content-Type-Options: nosniff, and Referrer-Policy: no-referrer.

05Low findings

L1Bin existence oracle (404 vs 401)Low

Without any token, GET /{hash}/requests returns 401 for a bin that exists and 404 for one that was never used. This leaks which bins exist and, combined with no rate limiting (M1), allows mapping of named bins. Data still requires the token, so impact is limited, but it aids targeting and the squatting attack (M2). Return an identical response (for example always 401 for well-formed names) regardless of whether the bin exists.

L2Overly permissive CORSLow

The preflight reflects an arbitrary Origin (Access-Control-Allow-Origin: https://evil.example) and advertises Allow-Methods: GET,POST,PUT,PATCH,DELETE,OPTIONS,HEAD and Allow-Headers: *; the capture GET returns Access-Control-Allow-Origin: *. Impact is low because reads require the secret X-Token header and no credentials are accepted, but the official reader is same-origin and the data API does not need CORS at all. Remove CORS from /requests, /events, and /clear, or restrict to a strict allowlist.

L3No HSTSLow

No Strict-Transport-Security header is sent. Railway terminates TLS and serves over HTTPS, but without HSTS a browser is not told to refuse future plaintext. Add Strict-Transport-Security: max-age=31536000; includeSubDomains once HTTPS-only is confirmed.

L4Captured secrets retained indefinitely under a single secretLow

Bins capture complete requests, including Authorization headers, cookies and bodies, and we observed these returned verbatim to the token holder. There is no expiry or retention limit, so anything sensitive sent to a bin lingers until the process restarts, guarded only by the one-time token (which cannot be rotated or revoked). Add an automatic retention/TTL policy, an explicit "delete bin" action, and a visible warning not to send production secrets to a shared bin. This pairs with the abuse caps in M1.

06Additional notes (informational)

  • Token in localStorage. The creation page auto-saves the token to localStorage and the viewer reads it back. Convenient, and safe given no XSS exists, but it raises the stakes of any future XSS, which is the main argument for the CSP in M3.
  • Client-side robustness. One interpolation in the viewer, r.httpVersion, is not HTML-escaped; it is not exploitable because Node's HTTP parser constrains it to digit.digit. The JSON syntax-highlight regex could behave pathologically on adversarial captured JSON, but only in the bin owner's own browser.
  • Prototype pollution. A {"__proto__": {...}} body was accepted and captured with no observable effect. Worth a quick code check that captured JSON is never deep-merged into objects server-side.
  • In-memory store. Captures appear to live in process memory, so a restart loses all data. This is a reliability point and the same surface that M1 protects.

Scope & method

Owner-authorized assessment of a live application. Active testing was deliberately bounded: no denial-of-service, no high-volume fuzzing or brute forcing, and no destructive operations against data the tester did not create. All state-changing tests (injection, clear, delete) were run against a tester-created bin (rtprobe7k2x9q); the owner's bin (/jomlat7cik49) was only read or probed and accumulated a handful of capture entries that can be flushed with Clear. Tools: curl, openssl, manual HTTP, and static review of the served HTML/JS. Raw artifacts are stored under capibara-redteam/raw/.
