Red Team & Security Assessment

Security, Privacy and Accessibility Review of nxtphase.ai

A non-destructive red team exercise covering the public attack surface: transport security, HTTP and email hardening, third-party scripts and supply chain, a reverse engineering pass of the custom code, GDPR and cookie handling, and WCAG accessibility.

Target https://nxtphase.ai Date 2 June 2026 Authorization Owner-requested (self-assessment) Method Passive analysis, no exploitation Platform Webflow + Cloudflare + Microsoft 365

01Executive summary

The site is a well built, lightweight Webflow marketing site behind Cloudflare. Transport security is strong, no secrets or trackers are exposed, and the single piece of custom JavaScript is clean. The meaningful gaps are not in exploitable code, they are in hardening and compliance: the site ships no Content Security Policy, the domain can be spoofed in email because DMARC and DKIM are absent, and there is no working privacy or cookie policy even though a contact form collects personal data.

No critical, directly exploitable vulnerability was found. There is no exposed API key, no injectable input that reaches a dangerous sink, no server-side code to attack (the site is fully managed by Webflow), and no information leak of note. The risk profile is therefore moderate and dominated by clickable, low-effort fixes that mostly live in the Cloudflare and Microsoft 365 dashboards rather than in code.

The five things to fix first

  1. Publish a DMARC record and enable DKIM so the nxtphase.ai domain cannot be used to send convincing phishing as your brand. (H2)
  2. Create and wire up a privacy policy and cookie statement. Both footer links currently point to # and are hidden, while the contact form asks visitors to agree to data processing. (H3)
  3. Add a Content Security Policy and security headers at Cloudflare to contain any future script compromise and stop clickjacking. (H1, M1)
  4. Add anti-automation to the contact form and make the consent a real, logged checkbox that links to the privacy policy. (M3, L5)
  5. Fix accessibility: restore visible keyboard focus and stop using the light brand green for normal text (it fails WCAG contrast). (M4, M5)

05aHigh severity findings

H1No Content Security PolicyHigh

What we found

No Content-Security-Policy header is returned on any page (confirmed on the home, contact and case-study pages, on both HEAD and GET requests, and there is no CSP <meta> tag). The browser will therefore execute scripts from any origin the markup references, with no allowlist.

Why it matters

The site pulls executable JavaScript from four external origins (Webflow CDN, CloudFront, the GSAP path, and assets.slater.app). Without a CSP, if any one of those origins is compromised, or if a stored cross-site-scripting payload ever reaches the page through Webflow CMS content, the attacker's script runs unconstrained: it can read the contact form, rewrite links, exfiltrate data, or inject a fake login. CSP is the single most effective containment control for a content-driven site.

Recommendation

Add a CSP at Cloudflare (Rules, Transform Rules, Modify Response Header) so it applies to every page without touching Webflow. Start in report-only mode, confirm nothing breaks, then enforce. A pragmatic starting policy for this stack:

Content-Security-Policy-Report-Only:
  default-src 'self';
  script-src 'self' 'unsafe-inline' https://cdn.prod.website-files.com
    https://d3e54v103j8qbb.cloudfront.net https://assets.slater.app;
  style-src 'self' 'unsafe-inline' https://cdn.prod.website-files.com;
  img-src 'self' data: https://cdn.prod.website-files.com;
  font-src 'self' https://cdn.prod.website-files.com;
  connect-src 'self' https://*.webflow.com;
  frame-ancestors 'none';
  base-uri 'self';
  form-action 'self' https://*.webflow.com;
  upgrade-insecure-requests;

Webflow injects inline scripts and styles, so 'unsafe-inline' is required unless you move to nonces (Webflow does not support nonces today). Even an inline-permitting CSP still blocks unknown external script origins and framing, which is most of the value.

H2Domain can be spoofed in email: no DMARC and no DKIMHigh

What we found

SPF is correctly set with a hard fail (v=spf1 include:spf.protection.outlook.com -all), which is good. However:

  • No DMARC record. _dmarc.nxtphase.ai returns nothing.
  • No DKIM. The standard Microsoft 365 selectors selector1._domainkey and selector2._domainkey are not published.

Why it matters

SPF alone does not protect the visible From address and does not survive forwarding. Without DMARC, receiving mail servers have no instruction to reject mail that fails authentication, and you get no reporting. For an AI consultancy that emails clients, this is a brand and social-engineering risk: an attacker can send invoices or "from the founder" phishing that appears to come from nxtphase.ai. This is the most realistic real-world attack against the organisation.

Recommendation

  1. Enable DKIM for the domain in the Microsoft 365 Defender portal, then publish the two CNAME records it gives you in Cloudflare DNS.
  2. Publish a DMARC record, starting in monitor mode and tightening once reports are clean: 
    _dmarc.nxtphase.ai  TXT
  "v=DMARC1; p=none; rua=mailto:dmarc@nxtphase.ai; fo=1; adkim=s; aspf=s"
    Move p=none to p=quarantine and then p=reject over a few weeks.
H3No working privacy or cookie policy while collecting personal dataHigh

What we found

The footer on every page contains placeholder legal links that are both non-functional and hidden:

<a href="#" class="footer_legal-link hide">Privacy</a>
<a href="#" class="footer_legal-link hide">Cookies</a>

Probing the obvious URLs (/privacy, /privacybeleid, /privacyverklaring, /cookies, /cookiebeleid, /voorwaarden, /disclaimer and more) all returned 404. Meanwhile the contact form collects name, company, email and a free-text message, and the form itself states "Ik ga akkoord met de verwerking van mijn gegevens" (I agree to the processing of my data).

Why it matters

Under the GDPR a Dutch company that processes personal data through a website must provide an accessible privacy statement describing what is collected, why, the legal basis, retention and data-subject rights. Asking the visitor to "agree to the processing of my data" with no policy to point to, and with the privacy link disabled, is a clear compliance gap and would not survive an Autoriteit Persoonsgegevens complaint. It is also a trust signal problem for a company that sells data and AI services.

Recommendation

  • Publish a privacy statement (privacyverklaring) and a short cookie statement. Both can be normal Webflow CMS pages.
  • Point the footer links at them and remove the hide class.
  • Link the privacy statement directly from the consent text under the contact form.

05bMedium severity findings

M1Clickjacking: no X-Frame-Options or frame-ancestorsMedium

What we found

No X-Frame-Options header and no CSP frame-ancestors directive are present, so the site can be embedded in an <iframe> on any domain.

Why it matters

An attacker can frame nxtphase.ai inside a malicious page and overlay it to trick a visitor into clicking the contact submit or other controls (clickjacking / UI redress). Impact is limited because the site has no authenticated actions, but it also enables convincing brand-impersonation pages.

Recommendation

Add at Cloudflare: X-Frame-Options: DENY and frame-ancestors 'none' in the CSP from H1.

M2No Subresource Integrity on the GSAP and Slater scriptsMedium

What we found

jQuery and the Webflow chunks are loaded with correct integrity (SRI) hashes. However the five GSAP scripts and the custom Slater script are loaded with no integrity attribute:

<script src="https://assets.slater.app/slater/20269/61392.js"></script>
<script src="https://cdn.prod.website-files.com/gsap/3.15.0/gsap.min.js"></script>
... (ScrollTrigger, SplitText, DrawSVGPlugin, CustomEase)

Why it matters

The Slater file is hosted on a third-party S3 bucket outside your control. If Slater's account or bucket is compromised, attacker-controlled JavaScript executes on every page of nxtphase.ai with full access to the DOM and the contact form. With no SRI and no CSP (H1), there is nothing to stop it. This is the most likely client-side compromise path.

Recommendation

  • Preferred: move the Slater code into Webflow's site-wide custom code (footer) so it is served from your own first-party origin and covered by Webflow's SRI, removing the external dependency entirely.
  • Otherwise: pin each external script with an integrity hash, and constrain script origins with the CSP from H1.
M3Contact form has no CAPTCHA or anti-automationMedium

What we found

The contact form has no reCAPTCHA, Turnstile or hCaptcha, and no honeypot field. The only protection is Webflow's per-site form submission quota.

Why it matters

The form is trivially scriptable, so it is open to spam and automated abuse. Sustained automated submissions can exhaust your Webflow plan's monthly form limit, after which legitimate enquiries are silently dropped, a low-effort denial of a real business function.

Recommendation

Enable Cloudflare Turnstile or Webflow's built-in reCAPTCHA on the form. Cloudflare Turnstile is privacy-friendly and does not require a cookie banner.

M4Keyboard focus indicators are suppressedMedium

What we found

The stylesheet contains eight outline: 0 rules plus an outline: none, and no :focus-visible rules at all. Only a single outline: 2px solid #2895f7 exists (a Webflow default that covers some form fields). Interactive elements such as buttons, links and the custom "AI journey" tabs appear to have their focus ring removed without a visible replacement.

Why it matters

This fails WCAG 2.1 success criterion 2.4.7 Focus Visible (Level AA). Keyboard-only and switch users cannot see where they are on the page, which makes the navigation and the contact form hard or impossible to operate.

Recommendation

Add a global visible focus style, for example:

a:focus-visible, button:focus-visible, .w-button:focus-visible,
input:focus-visible, textarea:focus-visible, [data-journey="tab"]:focus-visible{
  outline: 3px solid #2D6F44; outline-offset: 2px;
}

Verify on the live site with keyboard tabbing. This finding is high-confidence from the CSS but the exact per-element behaviour is best confirmed in the browser.

M5Brand green text fails colour contrastMedium

What we found

The brand palette taken from the hero shader code is background #F9F6F1 (cream), primary green #3E9B5D and dark green #2D6F44. Computed WCAG contrast ratios:

Foreground on backgroundRatioNormal text (4.5)Large text (3.0)
Green #3E9B5D on cream #F9F6F13.22:1FailPass
White on green #3E9B5D3.47:1FailPass
Dark green #2D6F44 on cream5.62:1PassPass
White on dark green #2D6F446.05:1PassPass

Why it matters

Wherever the lighter green #3E9B5D is used for normal-size text, links or small UI labels on the cream background, or as a button fill with white text at normal size, it fails WCAG 1.4.3 Contrast (Minimum, AA). It is acceptable only for large headings (24px+ or 19px+ bold) and purely decorative elements.

Recommendation

Use the darker #2D6F44 (which passes comfortably) for any normal-size green text, links and button labels. Reserve #3E9B5D for large display text and decoration. Confirm final values against the live rendered components.

05cLow severity findings

L1HSTS without includeSubDomains or preloadLow

HSTS is present (strict-transport-security: max-age=31536000) but omits includeSubDomains and preload, so subdomains are not protected and the very first visit is not pinned. After confirming every subdomain serves HTTPS, upgrade to max-age=63072000; includeSubDomains; preload and submit to the preload list.

L2Missing hardening headersLow

Absent: X-Content-Type-Options: nosniff (stops MIME sniffing), Referrer-Policy (recommend strict-origin-when-cross-origin), and Permissions-Policy (recommend disabling unused features, for example camera=(), microphone=(), geolocation=()). Add all three at Cloudflare alongside the CSP.

L3No CAA DNS recordLow

No CAA record exists, so any certificate authority may issue a certificate for the domain. Add a CAA record allowing only the CAs you use, for example 0 issue "pki.goog" for Google Trust Services (and your Cloudflare-managed CAs) to reduce mis-issuance risk.

L4Contact form declared method="get"Low

The form markup is method="get" with no action. In normal use Webflow's JavaScript intercepts submission and sends it as an AJAX request, so this is usually harmless. But if JavaScript fails or is disabled, the browser falls back to a native GET, placing the visitor's name, company, email and message into the URL query string, where it is logged by the CDN and stored in browser history. Set the form method to POST in Webflow to remove the fallback risk.

L5Consent text is not a recorded checkbox and links nowhereLow

The contact form shows "Ik ga akkoord met de verwerking van mijn gegevens..." as a static text line. There is no checkbox input (confirmed: zero checkboxes on the page) and no link to a privacy policy. If you rely on consent as the legal basis you cannot demonstrate it (GDPR Art. 7). For a contact form, legitimate interest is usually the cleaner basis, in which case the wording should be a clear notice plus a link to the privacy statement rather than an "I agree" with no mechanism. Pair this fix with H3.

L6Language attribute does not match contentLow

The document declares lang="nl-NL" but the homepage hero and meta description are in English, while other pages are Dutch. Screen readers will pronounce the English homepage with Dutch phonetics. Set lang per page to match its primary language, and mark inline language switches with lang on the element (WCAG 3.1.1 / 3.1.2).

L7Aging front-end librariesLow

jQuery 3.5.1 (2020) is loaded. It is not known to carry an unpatched critical issue in this static, non-user-input context (the 3.5.0 XSS fixes are included), but it is well behind current. These versions are dictated by Webflow, so the action is to keep the Webflow project on a current export and re-check when Webflow updates its bundled libraries. Tracked as hygiene, not an active vulnerability.

06Cookie and tracking analysis

This was a focus area of the request, so it is treated separately. The result is, perhaps surprisingly, good on privacy and weak on documentation.

CookieSet byFlagsPurposeConsent needed?
_cfuvidCloudflare (server)HttpOnly; Secure; SameSite=None; session (no Expires)Supports Cloudflare rate limiting / bot managementGenerally classed strictly necessary
  • No analytics, tag manager or marketing pixels were found anywhere. No Google Analytics, no Google Tag Manager, no Meta or LinkedIn pixel, no Hotjar, no HubSpot. Confirmed across the home, contact and case-study pages and inside the only custom script.
  • No consent platform (no Cookiebot, OneTrust, CookieYes, Osano, Usercentrics) is present, and none is needed at the current cookie level.
  • The only cookie is Cloudflare's _cfuvid, which Cloudflare documents as strictly necessary and not used for cross-site tracking. On that basis a consent banner is arguably not required today.

The actual mistake is documentation, not over-tracking. Even with only a strictly-necessary cookie, the ePrivacy and GDPR expectation is a short cookie statement that discloses _cfuvid. Today the cookie statement link is dead and hidden (see H3 and L5). Recommendation: keep the privacy-friendly posture, add the cookie statement page, and if you later add any analytics, use a cookieless option (Cloudflare Web Analytics or Plausible) to avoid needing a consent banner.

07Custom code reverse engineering

The only developer-authored JavaScript is the Slater file (61392.js, 22 KB). It was fully decompiled and read line by line. It is a set of decorative animation routines:

  • initHeroGlow() renders a WebGL fragment-shader "glow" on hero canvases, reacting to mouse and scroll.
  • initSpineAnimation(), initAIJourney(), initWhyIcons(), initSolutionIllustrations() drive GSAP scroll animations, tabbed cards and SVG illustrations.

Security assessment of the custom code

CheckResult
Dangerous sinks (eval, Function(), innerHTML, document.write)None
Network calls (fetch, XMLHttpRequest, beacons)None
Cookies, storage or fingerprintingNone
Hard-coded secrets, keys or tokensNone
Untrusted input (reads only developer-set data-* attributes)Safe
Accessibility behaviourRespects prefers-reduced-motion; sets aria-selected; arrow-key tab nav

The code is clean and even thoughtfully built for accessibility. The only residual risk is not in the code but in where it is hosted: the third-party Slater S3 origin with no SRI and no CSP (see M2 and H1).

A wider check of the whole site found no exposed API keys, no .env or source-map leakage, no admin or staging endpoints in the sitemap, and consistent behaviour across all page types. There is no server-side application to assess because hosting is fully managed by Webflow.

10Remediation roadmap

Quick wins (dashboard only, hours)

  • Enable DKIM in Microsoft 365 and publish DMARC in Cloudflare DNS (H2).
  • Create privacy and cookie statements, wire up the footer links, remove hide (H3, L5).
  • Turn on Cloudflare Turnstile for the contact form (M3).
  • Add a CAA record (L3).

Short term (Cloudflare header rules, days)

  • Add CSP in report-only, then enforce; add X-Frame-Options, nosniff, Referrer-Policy, Permissions-Policy; strengthen HSTS (H1, M1, L1, L2).
  • Fix focus styles and switch normal-size green text to #2D6F44 in the Webflow Designer (M4, M5).
  • Set the contact form to POST and link the privacy statement from the consent line (L4, L5).

Hardening (project decisions)

  • Move the Slater script in-house or pin it with SRI, then tighten the CSP script-src (M2).
  • Re-check bundled library versions whenever Webflow updates (L7).
  • Per-page lang and inline language marking (L6).

Scope, method and tools

Passive, non-destructive assessment of publicly served content only. No exploitation, fuzzing, brute forcing, denial of service or active intrusion was performed, in line with assessing a live production site you own. Techniques: HTTP header and TLS inspection (curl, openssl), DNS enumeration (dig), retrieval and static analysis of HTML, CSS and JavaScript, reverse engineering of the custom script, deterministic WCAG contrast calculation, and well-known-path probing. Raw artifacts are stored under nxtphase-redteam/raw/.

Two Medium items (M4 focus, M5 contrast) are high-confidence from source analysis and should be confirmed against the live rendered page during the fix. All other findings are confirmed from collected evidence.
