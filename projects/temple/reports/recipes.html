Recipes

A recipe is one declarative file that becomes a working app. Drop it in blueprints/, restart Temple, and it exists: a data model, a workflow, permissions, an audit trail, a board on the dashboard, and a full agent surface over MCP. No code, no migration, no deploy step beyond the restart.

Recipes are written in TOML, YAML or JSON, whichever you prefer. All three parse to the same model and pass through the same gates.

The safety idea behind recipes is a closed pantry. A recipe can only combine ingredients the engine already knows: twelve property types, three guard kinds, four invariant kinds, four typed effects, five roles. It cannot express code. A hostile or broken recipe is refused at the door or rejected at write time, it is never executed.

Temple ships four starter recipes: flow (issue tracking, a strict state machine), pages (typed documents in databases), wiki (free-form pages with revisions and backlinks), and crm (a lead pipeline, authored in TOML as the reference example of a custom recipe). They are examples, not the product. The product is that you can write your own.

Quick start

A recipe is one declarative file. You write it, the engine interprets it. There is no code generation step and nothing to compile. The loop is:

  1. Write a file in blueprints/. The loader picks up .json, .yaml, .yml and .toml, nothing else.
  2. Restart the server. Blueprints are parsed once at boot and cached for the life of the process.
  3. Check the boot log. A recipe that fails to parse or verify is skipped, not half-loaded, and the server says so: [blueprints] skipped: <file>: <reason>. No warning means every file registered.
  4. Run npm run verify. It prints a PASS or FAIL per blueprint with each verifier level (L1 algebra, L2 reachability, L3 soundness, L4 property) and every finding, and exits non-zero on failure. This is the same gate the loader runs, so what passes here loads there.
  5. Open the dashboard. Your app is live at /app/<key> (a board view when the entity has a state machine), and the full spec the engine is enforcing is rendered at /app/<key>/blueprint.

Every MCP tool works against the new app immediately, with no extra wiring: query_entities, create_entity, request_transition and show_board all take the app key, so an agent can use a recipe the moment it loads.

The recipe file

A recipe is one declarative document dropped into blueprints/. Three formats are accepted, chosen by file extension: TOML (.toml), YAML (.yaml or .yml) and JSON (.json). The format is surface syntax only. All three are parsed into one identical model and validated by the same strict schema (parseBlueprintDocument in blueprint-schema.ts), so crm.toml and flow.json go through exactly the same pipeline.

Every object in the schema is a strict object: a key the schema does not know is a parse error, never silently ignored.

Top-level fields:

Field Type Constraint
key string must match ^[a-z][a-z0-9_-]*$, unique across all loaded recipes (a duplicate key skips the later file)
name string min length 1
kind string min length 1
version number positive integer
description string min length 1
entities array at least 1 entity type

key is the only identifier that allows hyphens. Entity type names, property names, state names and action names all use the stricter ^[a-z][a-z0-9_]*$.

Entity types

Each element of entities:

Field Type Constraint and engine behavior
type string, required ^[a-z][a-z0-9_]*$, the type name used in every API call
label string, required min length 1, singular display label
labelPlural string, required min length 1, plural display label
titleProperty string, required min length 1, must name a declared property (L1 verifier error otherwise). The engine derives the entity title from this property on every write, falling back to (untitled) when it is not a non-empty string
stateMachine boolean, optional when true and states are declared, new entities start in the initial state and the verifier runs the full L1-L4 state checks. When absent, entities have a null state
container boolean, optional declarative metadata accepted by the schema (the shipped pages recipe marks database as a container). The write pipeline does not branch on it
hasBody boolean, optional advertises that the type carries a markdown body. It is exposed in app metadata and the UI describes the type as having a markdown body. The create and update pipeline accepts a body argument either way; the flag tells clients to expect one
freeform boolean, optional declarative metadata accepted by the schema (used by the shipped wiki recipe). No branch in the write pipeline
versioned boolean, optional every create and every property update writes a row to the revisions table with a per-entity incrementing version. On transitions, a revision is written only when the transition's effects include write_revision
parentTypes string array, optional enables and constrains parenting. Creating with a parentId on a type with no parentTypes is rejected with '<type>' does not accept a parent. The parent must exist, live in the same app, and its type must be listed, otherwise parent must be one of: <list> (in <app>)
properties array, required at least 1 property
states array, optional see states and transitions
transitions array, optional see states and transitions
invariants array, optional see invariants
effects array, optional entity-level effects, run on create and on property update (subject to each effect's on filter)

Properties

Property names must match ^[a-z][a-z0-9_]*$. The type is a closed vocabulary of twelve values. Write-time validation (validateUserProperties in validation.ts) runs on all user-supplied properties: create arguments, update arguments and transition payloads. Two universal rules first:

  • An unknown property name is rejected: unknown property '<key>' on <type>; declared: <list>.
  • null or "" is always accepted for any type. Clearing a value is allowed; required-ness is enforced at create, not per write.
Type Accepted value Rejected with
title any string '<key>' must be a string
text any string '<key>' must be a string
richtext any string '<key>' must be a string
select a string that is one of options '<key>' must be one of: <options>
status a string that is one of options '<key>' must be one of: <options>
multiselect an array whose every element is a string in options '<key>' must be an array of options or '<key>' values must be from: <options>
number a finite number (typeof value === "number" and Number.isFinite), so NaN, Infinity and numeric strings all fail '<key>' must be a number
date a string Date.parse accepts '<key>' must be a parseable date string
checkbox a boolean '<key>' must be true or false
user a non-empty (after trim) string id '<key>' must be an id string
relation a non-empty (after trim) string id '<key>' must be an id string
url a string matching ^https?:\/\/\S+$ (http or https, no whitespace) '<key>' must be an http(s) url

Other property fields:

  • required (boolean): checked at create only, after defaults are merged. Any required property that is still empty (null, "", or an empty array) rejects with '<name>' is required. A required property also counts as guaranteed in the verifier's L3 check.
  • options (string array): the legal values for select, status and multiselect. If omitted on those types, no value passes.
  • default (any): applied at create as { ...defaults, ...userProperties }, so user values win and defaults can satisfy the required check. Defaults are engine-applied, not user-supplied, so they bypass the write-time validator; keep them legal for their type yourself.
  • relationType (string, optional): accepted by the schema for relation properties. The write-time validator checks relation values only as non-empty id strings.

Effect outputs (for example closed_at from set_timestamp, or backlinks) are trusted engine writes and bypass property validation entirely, like generated columns in a database.

States and transitions

States:

  • name: must match ^[a-z][a-z0-9_]*$.
  • initial (boolean, optional): the verifier requires exactly one initial state per state machine (expected exactly one initial state, found <n> is an L1 error). New entities are created in this state.
  • terminal (boolean, optional): a terminal state may only be exited through a transition marked reopen (an L2 error otherwise). Declaring no terminal state at all is an L2 warning.
  • Duplicate state names are an L1 error.

Transitions:

  • action: must match ^[a-z][a-z0-9_]*$ and be unique within the entity type (duplicate actions are an L1 error). This is the verb callers invoke.
  • from: either the literal "*" (legal from every state) or a non-empty array of state names. Calling an action from a state not in from is rejected at the validation stage: '<action>' is not legal from state '<state>'.
  • to: the destination state name.
  • reopen (boolean, optional): marks the transition as a legitimate exit from a terminal state. The verifier is the enforcer here; at runtime a reopen transition behaves like any other.
  • policy (optional array): roles drawn from the closed set owner, admin, member, viewer, agent. When policy is absent, any caller whose role holds the entity.transition capability may fire the action (in the default capability map that is owner, admin, member and agent; viewer is read-only). When policy is present, the caller's role must also be in the list, otherwise the rejection is action '<action>' is not permitted for role '<role>'. An empty list is present but matches no role, so it blocks everyone. The base entity.transition capability is required in all cases.
  • guards (optional array): evaluated against the prospective property set, that is the entity's stored properties merged with any properties in the transition payload, so a payload can satisfy a guard in the same call. The three kinds, per evaluateGuards:
    • propertyPresent: fails when the property is empty (null, undefined, "", or an empty array), with guard: '<prop>' must be set.
    • propertyEquals: strict equality against equals (!==), with guard: '<prop>' must equal <json>.
    • hasRelation: the same emptiness check, phrased for relation properties, with guard: relation '<prop>' must be set.
    • A guard whose prop is omitted is skipped, it passes vacuously.
  • effects (optional array): run after guards pass, computed on the prospective entity. Their property patch is merged in before invariants are checked, so an effect can both satisfy and violate an invariant and the engine will see it.

Invariants

Each invariant has an id (min length 1), a description (min length 1), a kind from a closed set of four, and a params record. At runtime checkInvariants evaluates them against the prospective state and properties on every create, update and transition; a violation rejects the write with reason <id>: <description>.

  • requiresPropertyWhenStateIn, params prop and states: violated when the prospective state is in states and prop is empty (null, "", or an empty array).
  • numberMinWhenPresent, params prop and min: skipped when the value is null or ""; otherwise violated when Number(value) < min.
  • requiredPropertyAlways, params prop: violated whenever prop is empty, in every state, on every write.
  • terminalNoExit: a runtime no-op (checkOne always returns false for it). It is verifier-only: the L2 check that a terminal state has no non-reopen exit is the enforcement.

Effects

An effect reference has a name from a closed set of four, optional args, and an optional on array limited to "create" and "update". When on is present the effect only runs when the current action name is in the list; the engine's create and update flows run with action names create and update, so on is the filter for entity-level effects. Transition effects run under the transition's own action name, so leave on off there.

Per effects.ts, effects are pure: they return a property patch and side-effect markers, and the transition layer performs any real I/O based on the markers.

  • set_timestamp: writes new Date().toISOString() into the property named by args.prop (default updated_at). The target property does not have to be declared; effect writes bypass validation (the crm recipe stamps an undeclared closed_at on win). Marker: set_timestamp:<prop>.
  • extract_backlinks: scans the entity body for [[...]] targets (regex \[\[([^\]]+)\]\], trimmed, deduplicated) and writes the resulting array to the backlinks property. Marker: extract_backlinks:<count>.
  • write_revision: emits only the marker write_revision. The transition layer then writes a revision row, but only when the entity type is versioned.
  • notify: emits only the marker notify. No I/O is performed by the engine.

Any other name is a parse error and cannot reach runtime.

Enforcement: the four gates

Gate 1, strict parse. Every object in the document schema is strict, and every vocabulary (property types, guard kinds, invariant kinds, effect names, roles) is closed. A typo or an invented capability fails loudly at parse time. Real messages from the parser:

invalid blueprint document: entities.0: Unrecognized key: "transtions"
invalid blueprint document: entities.0.transitions.0.guards.0.kind: Invalid option: expected one of "propertyPresent"|"propertyEquals"|"hasRelation"
invalid blueprint document: entities.0.effects.0.name: Invalid option: expected one of "set_timestamp"|"write_revision"|"extract_backlinks"|"notify"

The first five issues are joined with ; into one error.

Gate 2, the verifier gates registration. The loader (blueprint.ts) scans the blueprints directory in sorted order, picking up only .json, .yaml, .yml and .toml files. Each file is strict-parsed, checked for a duplicate key, and run through the L1-L4 verifier. Any failure means the file is not registered: parse errors are recorded as <file>: <error message>, verification failures as <file>: failed verification (L1 algebra, L3 soundness), not loaded, duplicates as <file>: duplicate blueprint key '<key>'. All skips are logged at startup ([blueprints] skipped: ...) and exposed via blueprintLoadIssues(). User-authored recipes go through exactly the same gate as the shipped ones. An unverified recipe never becomes an app.

Gate 3, the bouncer at write time. Every write funnels through transition.ts and returns either success or a rejection with a stage and reason. The stages are policy, guard, invariant, validation and notfound. In pipeline order:

For a transition (requestTransition):

Check Stage Example reason
Entity type exists validation unknown entity type <app>/<type>
Action exists on the type validation unknown action '<action>' for <type>
Entity exists notfound entity <id> not found
Role holds entity.transition policy role '<role>' cannot transition in <app>
Role is in the transition's policy policy action '<action>' is not permitted for role '<role>'
Current state is in from validation '<action>' is not legal from state '<state>'
Payload writes properties: role holds entity.update policy writing properties during '<action>' requires entity.update
Payload properties pass the type validator validation 'estimate' must be a number
Guards hold on merged properties guard guard: 'owner' must be set
Invariants hold on the prospective state and effect-patched properties invariant I_amount_non_negative: Amount, if set, must be zero or greater.

For create (createEntityChecked): unknown type (validation), entity.create capability (policy), property validation (validation), parent rules (validation, or notfound when the parent id does not exist), required properties after defaults (validation), then create effects and invariants (invariant). For update (updateProperties): entity.update (policy), missing entity (notfound), property validation (validation), update effects, then invariants against the current state (invariant).

Gate 4, append-only audit. Every successful create, update and transition inserts a row into the entity_transitions table recording org, entity, app, type, action, actor, from-state, to-state, the payload and the effect markers that ran. The repository layer only ever inserts into this table.

The verifier

verifyBlueprint runs four levels over each entity type. A level fails on any error finding; warnings are reported but do not fail the level. A recipe is only registered when all four levels pass.

L1, algebra. Structural identities: the titleProperty names a declared property, invariants and guards reference declared properties, exactly one initial state, no duplicate state names or transition actions, every from and to names a known state. Example finding: transition 'go' references unknown from-state 'a'.

L2, reachability. A graph walk from the initial state. Errors: a state unreachable from the initial state, and a terminal state with a non-reopen exit. Warnings: a non-terminal dead end, and no terminal state at all. Example finding: terminal state 'won' has a non-reopen exit.

L3, soundness. Model-checks invariants against entry paths instead of waiting for runtime. For requiresPropertyWhenStateIn, every transition into a covered state must guarantee the property: the property is required at create, or the transition guards on propertyPresent for that property, or every from-state is itself covered by the invariant. It also checks that requiredPropertyAlways targets a property that is required or defaulted, and that numberMinWhenPresent has a numeric min. Example finding: transition 'approve' can enter 'done' without guaranteeing 'assignee' (violates I_review_needs_assignee).

L4, property simulation. Runs 200 randomised legal action sequences of up to 12 steps each, cycling properties of type user between set and cleared, so guard-pass and guard-fail paths are explored for guards on those properties. Each step applies guards, effects and invariants exactly as the bouncer does, then asserts that invariants still hold after the applied step. Example finding: simulation reached state 'won' violating I_negotiation_needs_owner: A lead cannot be in negotiation or won without an owner. after 'win'. On success the level reports passed 200 randomised runs.

Worked example: an expense-approval recipe in YAML

We will build expenses: an expense moves draft to submitted to approved to paid, with a rejected branch that can be reopened. Here is the complete file, blueprints/expenses.yaml. It parses strictly and passes all four verifier levels as written.

key: expenses
name: Expenses
kind: expenses
version: 1
description: >-
  Expense approval. Drafts are submitted with an amount, approved or
  rejected by a human with rank, and paid out. Rejected expenses can be
  reopened back to draft.

entities:
  - type: expense
    label: Expense
    labelPlural: Expenses
    titleProperty: title
    stateMachine: true

    properties:
      - name: title
        type: title
        required: true
      - name: amount
        type: number
      - name: category
        type: select
        options: [travel, meals, software, office, other]
        default: other
      - name: receipt
        type: url
      - name: approver
        type: user
      - name: paid
        type: checkbox
        default: false

    states:
      - name: draft
        initial: true
      - name: submitted
      - name: approved
      - name: paid
        terminal: true
      - name: rejected
        terminal: true

    transitions:
      - action: submit
        from: [draft]
        to: submitted
        guards:
          - kind: propertyPresent
            prop: amount
        policy: [owner, admin, member, agent]

      - action: approve
        from: [submitted]
        to: approved
        guards:
          - kind: propertyPresent
            prop: approver
        policy: [owner, admin]

      - action: reject
        from: [submitted]
        to: rejected
        policy: [owner, admin]

      - action: mark_paid
        from: [approved]
        to: paid
        effects:
          - name: set_timestamp
            args: { prop: paid_at }
        policy: [owner, admin]

      - action: reopen
        from: [rejected]
        to: draft
        reopen: true
        policy: [owner, admin, member]

    invariants:
      - id: I_approval_needs_approver
        description: An expense cannot be approved or paid without an approver.
        kind: requiresPropertyWhenStateIn
        params:
          prop: approver
          states: [approved, paid]
      - id: I_amount_non_negative
        description: Amount, if set, must be zero or greater.
        kind: numberMinWhenPresent
        params:
          prop: amount
          min: 0

Four decisions worth walking through.

Guards make properties required at the moment they matter, not at create. amount is not required: true, because a draft is allowed to be empty while someone is still filling it in. The propertyPresent guard on submit is where the requirement bites: you cannot leave draft without an amount, and the rejection comes back as guard: 'amount' must be set. The numberMinWhenPresent invariant then keeps any amount that is set at zero or above, on every write, including plain property updates.

The invariant has to be provably safe, and the verifier checks the proof. I_approval_needs_approver says approved and paid expenses always have an approver. L3 soundness model-checks this at load time: every transition into a protected state must guarantee the property, either by a propertyPresent guard on that transition, by the property being required at create, or because every from-state of the transition is itself covered by the invariant. This design passes because the only way into approved is approve, which guards on approver, and the only way into paid is mark_paid, whose sole from-state approved is already covered, so the property cannot have been lost on the way. If you dropped the guard from approve, the file would not load: transition 'approve' can enter 'approved' without guaranteeing 'approver' (violates I_approval_needs_approver).

Terminal states may only be exited by an explicit reopen. Both paid and rejected are terminal. paid has no exits at all. rejected has one, and it carries reopen: true; without that flag L2 rejects the file with terminal state 'rejected' has a non-reopen exit. Reopening goes back to draft, so a reopened expense re-earns its way through the same guards.

Policy splits the work between agents and humans. submit lists agent, so an agent can move a draft forward. approve, reject and mark_paid list only owner and admin: spending decisions stay with humans who hold rank. Note that creating a draft is not governed by transition policy at all, it is the entity.create capability of the role, which agents have, so agents may draft and submit but an agent calling approve is bounced at the policy stage. One last detail: the paid checkbox and the paid state share a name but live in different namespaces, the checkbox is data on the entity, the state is a node in the machine, and paid_at is written by the set_timestamp effect as a trusted engine write, which is why it does not appear in properties.

When things are rejected

Every write is funneled through the same pipeline (policy, then from-state and payload validation, then guards, then effects, then invariants), and every rejection names its stage and reason. Load-time problems never reach runtime: a bad file is simply not registered. The messages below are the real shapes, with this recipe's names filled in.

Failure When Stage Message
Unknown property in create/update/payload runtime validation unknown property 'snack' on expense; declared: title, amount, category, receipt, approver, paid
Wrong value type runtime validation 'amount' must be a number (also 'paid' must be true or false, 'receipt' must be an http(s) url, 'approver' must be an id string)
Select value not in options runtime validation 'category' must be one of: travel, meals, software, office, other
Action not legal from current state runtime validation 'approve' is not legal from state 'draft'
Guard not satisfied runtime guard guard: 'amount' must be set
Role not in the transition's policy runtime policy action 'approve' is not permitted for role 'agent'
Invariant would be violated runtime invariant I_amount_non_negative: Amount, if set, must be zero or greater.
Parent not allowed by parentTypes runtime validation 'expense' does not accept a parent or, on a type that declares parents, parent must be one of: database, page (in pages)
Typo key in the recipe file load parse error invalid blueprint document: entities.0: Unrecognized key: "transtions"
Vocabulary violation (guard kind, effect name, property type) load parse error invalid blueprint document: entities.0.transitions.0.guards.0.kind: Invalid option: expected one of "propertyPresent"|"propertyEquals"|"hasRelation"
Verifier finds an error load skipped boot log: [blueprints] skipped: expenses.yaml: failed verification (L3 soundness), not loaded
Two files claim the same key load skipped boot log: [blueprints] skipped: expenses2.yaml: duplicate blueprint key 'expenses'

Two things to internalize. First, the schema is strict and every vocabulary is closed: a misspelled key like transtions is a loud parse error, never a silently dropped rule, and there is no way to smuggle in a guard kind or effect name the engine does not ship. Second, a skipped file is invisible to the running system, so if your app is missing from the dashboard, the boot log warning is the first place to look, then npm run verify for the full finding list.

Authoring with an agent

An agent authors a recipe the same way you do, because there is no other way. Claude writes the file into blueprints/, the server restarts, the strict parser and the L1-L4 verifier decide whether it loads, and npm run verify gives the agent the same findings to iterate against. There is no privileged path that skips the gate.

The same symmetry holds at runtime. When an agent later uses the app over MCP, every create_entity, update_properties and request_transition call runs through the identical bouncer pipeline as a human in the UI: same property validation, same guards, same invariants, and a policy check against the agent role. In the expenses recipe that means an agent can draft and submit all day, and its attempt to approve is rejected at the policy stage with the same policy-stage rejection a human without the required role would get. The recipe is the contract, and it binds both kinds of author equally.

Format notes

TOML, YAML and JSON all describe the same model. The file extension picks the parser, and from that point on parsing, verification and enforcement are byte-for-byte identical, so choose by taste.

  • TOML reads well for long recipes because nothing nests visually. The cost is repetition: every property, state and transition is its own [[entities.properties]], [[entities.states]] or [[entities.transitions]] block, and inline tables carry the small structures, for example guards = [{ kind = "propertyPresent", prop = "amount" }]. See blueprints/crm.toml for the shipped example.
  • YAML is the most compact, but indentation is structure. A transitions: block indented one level too deep becomes a stray key on the wrong object, and the strict schema turns that into an Unrecognized key parse error rather than a silent no-op, which is the failure you want, just be ready for it.
  • JSON is the natural choice for machine generation: no indentation semantics, no comments to lose, and trivially produced by serializing a validated object. See blueprints/flow.json for the shipped example.
