How Temple works

The life of an entity: how blueprints define the rules, how every write is forced through one gate, and why no actor, human or agent, can put the data into a state the blueprint forbids.

The big picture

Temple is one PostgreSQL database, one enforcement gate, and a set of blueprints that declare what is allowed. Nothing writes to the database directly. The web portal, every agent over MCP, the seed script, the test box in the blueprint editor: all of them produce proposals, and one pipeline decides.

Every caller resolves to an actor: a user, a role, and a mode. The bouncer enforces the blueprint against that actor on every single write.

Blueprints: rules as data, never code

A blueprint is a declarative document (YAML by convention, TOML and JSON also parse) that defines an app: its entity types, their typed properties, and, where wanted, a full state machine with guards, invariants, effects and role policy. The engine interprets blueprints; it never executes them. Everything a blueprint can say comes from a closed vocabulary:

The parser is strict: an unknown key, a misspelled section, a guard kind or effect name outside these lists is a loud parse error, never a silently dropped rule. A hostile blueprint cannot smuggle in behavior, because there is no way to express behavior. The worst a bad blueprint can do is be refused.

Anatomy of a blueprint. The schema part is enough for a governed list (wiki, pages); add states and transitions and it becomes a workflow (flow, crm).

From editor to live app

Blueprints live in the database as append-only versions. The portal's IDE is the editor; the files shipped in blueprints/ only seed an empty store. Saving and publishing walk a fixed lifecycle:

A draft that fails verification saves fine, but it is inactive everywhere and refuses to publish. Publishing re-verifies and swaps the in-memory registry: the app updates mid-flight.

  • Versions are append-only. Every save is a new row with the verbatim source, the parsed spec, and the verifier report. History is never rewritten; old versions load back into the editor.
  • Two registries serve reads. The published registry holds the latest published spec per key. The draft registry is the published set overlaid with any verified draft newer than the last publish.

The write path: one gate, no exceptions

Every mutation, whether it is a create, a property update, or a state transition, runs the same pipeline. The caller's identity was resolved before the engine is ever reached; from there the blueprint drives every decision. A rejection names its stage and its reason, verbatim:

The pipeline for request_transition. Creates run the same gate minus the state-machine stages: policy, schema validation, parent rules, required properties, entity-level effects, invariants, then commit. Updates run it too, but parent rules and required-ness are create-time checks; keeping a property forever takes an invariant.

The stages, precisely

  • Policy is two layers. First the role must hold the coarse permission (entity.transition, from the role matrix; a viewer fails here). Then the transition's own policy list is checked: flow's approve lists owner, admin, member, so an agent passes layer one and is still refused by name at layer two. Writing properties inside a transition payload additionally requires entity.update.
  • Validation never trusts input. Each payload property must be declared on the entity type and match its type: a select value must be one of its options, a multiselect must be a subset, a number must be finite, a user must be an id string, an unknown key is rejected by name. Parent rules also live here: a child may only attach to a declared parentType, in the same app.
  • Guards see the merged picture. Preconditions evaluate against current properties plus the validated payload, so "set the owner and enter negotiation" works in one move, while "enter negotiation without an owner" is blocked.
  • Effects are computed before invariants. Effects are pure functions from the closed library: they return a property patch (a timestamp, extracted backlinks) and markers (write a revision). They cannot reach the network or the database.
  • Invariants judge the future, not the past. The check runs on the state the entity is about to be in, with the patched properties. If the prospective state violates any invariant, nothing is written at all.
  • Commit is three writes in strict order. The row is updated, a revision is written for versioned types (on transitions, only when the effects asked for one), and an audit row is appended with actor, action, from-state, to-state, payload and mode. The pipeline is the only code that touches entity rows, so every accepted write arrives with its audit row.
The same pipeline serves everyone. The portal's test box, an agent over MCP, the owner in a hurry: identical stages, identical rejections. Trust comes from there being exactly one door.

States and transitions, enforced

A state machine in a blueprint is not documentation, it is the complete list of legal moves. Flow's issue tracker, as shipped:

Also defined but not drawn: reject (in_review back to in_progress), cancel from any active state, and reopen (done or canceled back to backlog, owner and admin only, flagged as a deliberate terminal exit).

Three mechanisms make this real rather than advisory:

  • Legality. An action not listed for the current state is rejected outright: 'approve' is not legal from state 'backlog'. There is no way to skip a step, because skipping is simply not a defined move.
  • Guards. submit_review carries propertyPresent: assignee: unassigned work cannot enter review, no matter who asks.
  • Invariants. I_review_needs_assignee declares that an issue in in_review or done always has an assignee. Even a move that passes its guard cannot land the entity in a state that breaks this; the prospective check catches it first.

The verifier: proving the rules before trusting them

Enforcement at runtime is only as good as the rule set, so no blueprint becomes active without passing a four-level gate. The levels are layered like slices of Swiss cheese: no single level catches everything, together their holes do not line up.

LevelQuestion it answersExample finding
L1 algebraIs the machine well-formed? Exactly one initial state, no duplicate states or actions, every transition references states that exist, every guard and invariant references a declared property.transition 'go' references unknown to-state 'ghost'
L2 reachabilityCan every state be reached from the initial state? Do terminal states stay terminal unless a transition is explicitly marked reopen? Those two are errors that block registration; a non-terminal dead-end state is flagged as a warning.state 'b' is unreachable from initial state
L3 soundnessCan any sequence of legal moves violate an invariant? Every transition into a protected state must guarantee the protected property: by a guard, by the property being required, or by every from-state already being covered.transition 'close' can enter 'closed' without guaranteeing 'owner' (violates I_owner_at_close)
L4 propertyDoes it hold under fire? Two hundred randomised runs of legal action sequences, cycling user-typed properties between set and cleared, asserting after every applied move that all invariants still hold.simulation reached state 's' violating I_x after 'action'

The same verifier runs in three places: live in the editor's Verify button, as the gate on every draft save and publish, and as npm run verify against raw seed files. A blueprint that fails is recorded with its report, stays inactive, and refuses to publish.

Two worlds: published and draft

Every actor carries a mode, fixed at authentication. Portal sessions and published tokens operate on production. A draft token opens the parallel world: it sees published blueprints plus verified drafts, and everything it writes is tagged draft.

  • Draft entities never appear on production boards, in production queries, or to published MCP connections; the tag rides on the entity and on every audit row.
  • This is what makes the editor's test box safe: it runs the full real pipeline, as you, in the draft world. You can exercise a half-built workflow with real writes and real rejections without touching production data.
  • Publishing a blueprint does not migrate draft data; the draft world is a workbench, not a staging copy.

The audit trail: history is not optional

Two append-only records accompany every entity:

  • entity_transitions gets one row per accepted write: create, update, or transition, with the actor, the action, from-state, to-state, the payload, the effects that ran, and the mode. It is written inside the commit stage; there is no accepted write without it.
  • revisions snapshots versioned entity types (pages, wiki) on every create and update: full title, body and properties, so any document's history can be replayed.

This is why a card on the Flow board can show its full story: filed by the agent, started, submitted for review, approved by a named human, each step timestamped, none of it editable after the fact.
