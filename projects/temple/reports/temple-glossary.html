The vocabulary of agent-built software.

Terms and ideas worth keeping from Sesh Nalla's talk, "How Datadog built a universal machine tool for Claude Code." Two tags below: Datadog marks something specific to their work, an untagged term is a general concept you can reuse.

Source: Datadog (Sesh Nalla, VP Engineering), Anthropic conference talk. Captured for the Temple project by Incredicorp.

01

The central metaphor

The frame the whole talk hangs on: borrowing from manufacturing to describe what agents now need.

Machine tool

In manufacturing, a tool (jig, fixture, gauge, mill) that produces precise, repeatable parts which assemble into larger machines, engines, aircraft, reactors. The breakthrough of industrialisation, because it enabled scale through interchangeability, standardisation and precision.

Applied to software: instead of an agent improvising a one-off tool for every local need, it produces a precise specification that can be run repeatably. The metaphor is the spine of the entire Temple idea.

Mechanisation vs. industrialisation

Mechanisation means agents simply do more of the work. Industrialisation means the work itself becomes repeatable, verifiable, controllable and scalable, the actual jump that matters.

Temple is an industrialisation play, not a "let the agent do more" play. The difference is governance and verification, not raw output.

Dark factory

A term popularised by Simon Willison. A software process where agents keep working on the virtual factory floor without humans present, you can "turn off the lights." The human role shifts to designing the factory: the constraints, the outcomes, and the verification loop, so it can run for hours, days or weeks unattended.

This is the operating model Temple sells: the client stops working tools and starts designing the factory that runs them.

Directed evolution · cultivating software

The closing idea: software built this way behaves less like a built artefact and more like an organism you grow through feedback, selection and adaptation. Closer to agriculture than construction, you choose the direction the software evolves in.

02

Datadog's lineage

Four projects, each of which exposed the bottleneck for the next.

Courier Datadog

A distributed queuing system built from scratch in 2024, entirely by hand, before agents. Rigorous formal modelling and simulation. Took roughly a year. The baseline against which agent-era speed is measured.

Bits Evolve Datadog

A closed-loop evolutionary optimisation harness (September 2025), inspired by DeepMind's AlphaEvolve. A council of models, large and small, generate code variants for "hot" functions; a cascade of benchmarks, tests and production observability decides what survives. Natural selection for code.

Key lesson: evolution is only as good as the environment it adapts within. Bad benchmarks breed bad code; weak observability yields shallow gains.

Helix Datadog

A Kafka-comparable streaming service built mostly by Claude Code with one human steering, working in days, not the year Courier took. Shadowing real production workloads, and in places looks 2–5× cheaper than the current solution.

Proved agents can build large systems fast. Also exposed the next wall: getting from "works" to production-trusted.

AlphaEvolve

DeepMind's evolutionary code-optimisation system, the cited inspiration for Bits Evolve. Models propose, an automated evaluator selects.

03

The Tempor mechanism

How the machine tool actually works. This is the part Temple adopts most directly.

Tempor Datadog

Datadog's machine tool. Instead of an agent inventing disconnected tools, it produces a precise specification of intent and domain, which a deterministic layer compiles, verifies and deploys into a runtime. Used three ways: an agent control plane, a way for agents to build their own small tools, and a control API for Helix.

Near-namesake of this project, Temple. Same engine, reframed by Incredicorp as a product for regulated mid-market.

Blueprint

The declarative artefact the agent produces over several turns, its "plan mode" output, but precise rather than a markdown file. It declares: what the states are, which transitions are legal, who may request them, what effects are allowed, what invariants must hold, and what happens when a tool call fails.

Transition table

The compiled blueprint. The critical control logic rendered as data, not spaghetti code, interchangeable, checkable, and not hidden inside an improvised chain of service methods. Agents can change it dynamically with safety.

Formal state transitions

Representing the application's shape as a precise transition system. "Formal" here does not mean every property is mathematically proven; it means the basic shape is explicit and precise, far better for both humans and agents to reason about than arbitrary code.

Compiler outside the LLM

The agent generates a structured description; a deterministic compilation step, not the LLM, turns it into the runtime shape and verifies it. Analogy: you write Rust, the Rust compiler checks it. The abstraction is raised so the model never emits arbitrary application code directly.

Effect system · typed effects

Deliberately small, typed operations (popular in typed runtimes). Keeping effects small prevents the state machine from becoming a backdoor for arbitrary behaviour.

WASM modules

Where genuinely arbitrary, LLM-generated code is allowed to live, in one narrow, inspectable place, when a typed effect is not enough. Contains the blast radius.

Policy gates

Because the transition table is data, who-may-do-what is evaluated together with the transitions: which actions an operator agent may take, which are forbidden to a builder agent, whether a completed rollout can run again. Permissions as data, not scattered code.

04

Verification

"Verification is basically the bottleneck right now for pretty much everything." The most reusable section of the talk.

Verifier · the Swiss-cheese pattern

A multi-level gate run before a transition table loads into the runtime. No single level needs to catch everything; layered, their gaps do not line up. The agent can judge how many levels a given change needs.

The four levels

L1 algebra, check the algebra of the automaton. L2 model-check, explore the reachable state graph, can any path reach a bad state? L3 fault injection, run schedules and inject failures, do the invariants survive bad timing? L4 property tests, randomised action sequences, the technique the speaker most encourages teams to learn.

Invariants

Properties that must hold in every reachable state (e.g. "a deal cannot reach 'won' without a linked transcript"). The thing the verifier proves, and the thing a missing-condition bug violates.

Model checking

Exhaustively exploring the reachable states of the system to prove no path reaches a forbidden state. Borrowed from high-assurance systems engineering.

Property testing

Generating random but legal action sequences and asserting invariants survive all of them, instead of hand-writing individual test cases.

Verification cascade

The staged gate from Bits Evolve, benchmarks, then tests, then production observability, that decides which generated variant survives. The ancestor of the verifier.

Idempotent vs. non-idempotent effects

An idempotent effect can be re-run safely (a read). A non-idempotent one cannot, the talk's example is patching a Kubernetes stateful set, which needs a callback to confirm success or fail, and a compensation path.

Mileage Datadog

The operational track record a system must earn before production: proof it can run, and that multiple people, not just its builder, can operate it. Helix had capability but lacked mileage.

Proof-carrying change

A change that arrives with the evidence of its own safety, so a human does not have to review every candidate the system generates. The compounding mechanism that lets the factory run unattended.

05

Runtimes

The prior art Tempor stands on, decades-old, high-assurance, suddenly relevant again.

Erlang · BEAM · OTP

An actor runtime with hot code loading and high-assurance heritage (telecoms). The precedent for deploying a new transition table into a running system without a full deploy cycle. The speaker calls hot-deploying into BEAM a "creative way of using runtimes hardened over high-assurance systems for agents to work with."

Temporal · durable execution

Workflow engines and durable-execution runtimes that popularised a precise runtime for "invincible" applications, ones that survive crashes and resume. Same family of idea: make the operational model explicit and the runtime guarantee it.

Hot reload / hot deploy

Loading a changed transition table into the live runtime without going through CI and deployment. Lets an agent working overnight make real, safe progress without a human in the deploy loop.

Control plane vs. data plane

The control plane manages lifecycle, sessions, roles and policy; the data plane does the actual high-throughput work. Tempor served as a control API around the Helix data plane.

Agent control plane

Using the machine tool to manage cloud-managed agent sessions, their roles, the work they take, and their operational lifecycle, precisely, rather than ad hoc.

06

The human shift

What changes for the people, the disorientation, and where the bottleneck keeps running to.

Bottleneck moving

The throughline. Courier's bottleneck was construction; Bits Evolve moved it to the feedback loop; Helix moved it again to humans coordinating to ship agent-built work to production through human-shaped tools.

Amdahl's law

Cited via Dario: the serial part of a process caps how much the parallel part can speed it up. When agents are fast, the slow human-coordination step becomes the dominant limit, hence the push to industrialise it away.

Opus 4.5 inflection point Datadog

The moment, around late 2025, when the speaker's ambition curve bent upward and he began trusting Claude with larger, more ambiguous, system-scoped work, even databases. Progressive, earned through many experiments, not sudden.

Shaping the work

The new mode of engineering. You no longer write the code; you decide what the agent sees, what tools it has, what success means, and how failure is detected.

Altitude of working

The rising abstraction level. "Everyone's promoted three levels up the management chain," disorienting, "pushed against gravity very fast," especially for engineers who love reading code.

The seven stages of grief

The speaker's wry name for engineers adjusting to not seeing code day to day. He has made his peace; many have not.

Judgment-bearing roles

Cloud-managed agents that no longer just follow instructions but make their own decisions, run for hours or days, and construct their own tools mid-session.

False progress

The failure mode of unmanaged agents: lots of fast output, some useful, some illusory, and a blur between throwaway session tooling and the actual product. The problem the machine tool exists to remove.
