nxtflow — how we ship

One sentence: small verified batches, an always-current living report, honest write-backs to the tracker, and never optimize or destroy anything without a measured baseline and a rollback. Distilled from the Elastofirm Profiler build (38 stories shipped, a 31-test regression suite, a safe CLI, a measured matcher-optimization cycle) into a portable skill + CLAUDE.md + plugin.

1 · The Loop

pick 2-3 stories→ branch per batch→ build (+version bump)→ extend + run regression suite→ verify LIVE (screenshot = proof)→ living board + deploy + share→ tracker write-back, honest→ commit
  • Pick: surface the most shippable items (blockers checked first), offer them as option cards with previews; the human picks. If the backlog is mostly blocked, produce a blockers report instead of building stubs.
  • Verify live: drive the real running app with browser automation; the screenshot showing the component working becomes the proof image on the board and in reports.
  • Living board: one self-contained HTML, always current: in-development expanded, verified collapsed with a "Show proof image" button, flagged items with their open questions, and the full still-ahead backlog with rendered specs. PIN-gated deploy so stakeholders see truth, not promises.
  • Honest write-back: a story reaches In Review only with a comment naming what shipped, what deviates from the spec, what is explicitly NOT done, and the caveats. Scaffolding is labelled scaffolding. Reverts are labelled reverts.

2 · Honesty norms

  • Never claim more than was verified — and say how it was verified.
  • Requirements unclear? Build nothing: revert, flag the story, list the questions. (Cheaper than shipping the wrong thing.)
  • Feature not good enough? Pull it from the app, mark it "not done — revisit", return it to the backlog everywhere.
  • Source data missing? Scaffold end-to-end with a subtle na pill so everything lights up the moment data arrives.
  • Security findings get fixed AND pinned shut with a regression test in the same batch.

3 · Output standard

Every readable artifact is HTML

  • Single self-contained file, inline CSS, in artifacts/
  • Light default + Light/Dark/System toggle, Geist fonts, print CSS
  • Collapsible story cards with id/estimate/status badges
  • Proof screenshots behind click-to-reveal buttons (never inline)
  • Mermaid diagrams rendered client-side (source as fallback)
  • Search + sort bar on long lists (status / points / id / text)
  • Archived centrally + pushed to the artifact platform as a new version

The report family

  • Verification board — the living "what is done & how to check it"
  • Full task list — every story rendered: why, code analysis, steps, challenges, drawn diagram, customer verify steps, proof image
  • Status & blockers — remaining work grouped by what unblocks it, naming the single highest-leverage unblocker
  • Feature screenshot gallery — one card per shipped component
  • Generated by the task-report skill from Linear / transcript / Notion; verify steps written back to the tracker idempotently

4 · Tracker conventions

  • Numbered milestones (1 · Rollen en toegang); stories carry: Waarom (PO quote), Code-analyse (against the real code), Implementatie stappen, Mogelijke uitdagingen, and a mermaid Diagram.
  • Statuses: Backlog → In Review (shipped + verified, with the honest comment) → done; cancelled stays visible with its reason.
  • Verification steps live on the story as a single marker-tagged comment (**How to verify** · _task-report_) — updated on regeneration, never duplicated.
  • List APIs truncate long descriptions: fetch per-story for full text (delegated to a subagent writing a file).

The rules that make it work

  • Verbatim quotes only. The Waarom quote is lifted from the transcript untouched; no usable quote → no quote (never paraphrase-as-quote).
  • Code-analyse against the real repo. Files, functions, line refs — a survey subagent reads the code before a single story is written. This is what makes a story executable without re-research.
  • Estimates by scope: S=1 (a field/toggle) · M=3 (component + endpoint) · L=5 (module/migration) · 8 = big/spike.
  • Ambiguity is content: open product decisions are written into Mogelijke uitdagingen — a named open question beats a wrong story.
  • Numbered milestones (2 · Gebruiksstatistieken) so every report sorts correctly; one simple mermaid flow per story.
  • Checkpoint before bulk-create, dedupe by title, addenda (e.g. a legal-text email) append to the same project with the source text verbatim where it must ship as written.

6 · Eval-before-optimize

baseline harness (seeded, production code path)→ blind LLM-as-judge→ experiment rig (parity-checked)→ full-scale validation→ flag-gated rollout, instant rollback
  • No tuning without a number that will move. Identity-variant below 100% is itself a finding (near-duplicates, index drift).
  • The judge sees query + candidates blind (shuffled, no ids, no ground truth); structured outputs; visual report with every judgment eyeball-able.
  • The rig is only valid after a parity check (its base arm reproduces production vectors at cosine ~1.0) — then arms compare relative to base.
  • Winners ship as new artifact files behind an env-var version switch; the old pipeline stays untouched; rollback is flip + restart.
  • Proof from the source project: rot15 retrieval 36% → 92% top-1 (100% top-5), validated against 11,978 distractors, before a single production file changed.

7 · Safe project CLI

  • One entry point (<project> <group> <command>): status · data · index · export · eval · db · admin. Stdlib argparse, importing existing modules.
  • Read-only unless --apply (dry-run prints the exact delta) · auto-backup before destructive writes · typed confirmations (--yes skips prompts, never backups) · lock file · history log · read-only DB connections · merge-don't-replace ingestion · --overwrite required to clobber exports · exit codes 0/1/2/3.
  • Deny paths are smoke-tested explicitly; destructive logic is proven on a copy of the database first.

8 · Agent working style

  • Bulk fetches and wide surveys → subagents that write files; the main context stays lean.
  • Long computations → background tasks, reported on completion. Independent questions → parallel agents.
  • Big builds start with an HTML plan artifact (parameter-level, with open questions) and an explicit wait for go.
  • Direction forks → 2-4 concrete option cards with previews, not essays.
  • Environment traps (alias-corrupted heredocs, stale dev servers, Radix pointer events, shadowed Image, CORS-tainted canvases, argparse flag hoisting …) are codified in references/gotchas.md — read once per project.
