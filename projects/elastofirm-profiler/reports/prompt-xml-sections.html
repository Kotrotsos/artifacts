Flat prompt vs. XML-tagged sections

The same task written two ways. Tagging the parts (role, rules, input, output) makes a prompt easier for the model to parse and for you to edit and reuse.

Avoid Without sections

Everything in one blob — instructions, data and the output rule are tangled together.

You are a technical writer for a rubber profile manufacturer. Write a short
product summary for the profile below. Keep it under 80 words, use plain
language a salesperson can read out loud, don't invent specs that aren't given,
and end with the typical application. The profile is: article RP-14207, a hollow
D-seal in EPDM 65 Shore A, surface 1.18 cm², meter weight 168 g/m, produced on
the LCM line, last produced April 2026, used for window and door sealing. Also
if the meter weight is missing just say "weight on request" instead of guessing.
Return just the summary text, no headings.

Prefer With XML-tagged sections

Each concern gets its own tag: role, task, instructions, input data, output format.

<role>
You are a technical writer for a rubber profile manufacturer.
</role>

<task>
Write a short product summary of the profile in <profile>.
</task>

<instructions>
- Maximum 80 words.
- Plain language a salesperson can read aloud.
- Use only facts given in <profile>; never invent specifications.
- If meter_weight is missing, write "weight on request" instead of a number.
- End with the typical application.
</instructions>

<profile>
article_number: RP-14207
type: hollow D-seal
compound: EPDM 65 Shore A
surface_cm2: 1.18
meter_weight_g_per_m: 168
process: LCM
last_production: 2026-04
application: window and door sealing
</profile>

<output_format>
Return only the summary text, no headings or preamble.
</output_format>

Why the tagged version is better

  • Separation of concerns — the model (and you) can tell instructions from data from format at a glance.
  • Easy to edit & reuse — swap the <profile> block for the next record without touching the rules. Ideal for templating across many items.
  • Fewer instruction-injection mistakes — text inside <profile> reads as data, not as commands.
  • Reliable referencing — you can point at a section ("the profile in <profile>") and models follow it well.

Rules of thumb: use lowercase, descriptive tag names; keep them consistent; nest only when it adds clarity (e.g. several <example> blocks inside <examples>); and don't bother tagging tiny prompts — the payoff appears once a prompt has distinct parts (role, rules, context, input, format) or gets reused.
