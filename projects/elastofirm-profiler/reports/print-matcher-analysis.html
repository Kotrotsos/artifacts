Can the print-matcher power Elastofirm's image search?

Comparison of the shoe-print matching service (~/personal/print) against Elastofirm's current profile matcher, and a concrete integration proposal. Short version: yes — as a second stage, not a replacement. The print-matcher's ORB + RANSAC rescoring is what buys partial-image matching and could cut Elastofirm's search latency by an order of magnitude; its global descriptor is a sidegrade. One real technical risk needs a pilot before committing.

2 · Why the print-matcher can match partial prints (and Elastofirm can't)

Elastofirm: one global fingerprint

The whole image becomes a single 8,100-dim HOG vector. Crop away half the profile and the vector changes everywhere — the gradient histogram of "the full cross-section" and "the left half, zero-padded" are simply different fingerprints. Cosine similarity has no notion of "this region matches".

Print-matcher: many local fingerprints + geometry

ORB extracts hundreds of local keypoints; each describes a small patch. A partial query still produces keypoints for the region it does have. RANSAC then demands the matched keypoints agree on one geometric transform — so a half-print that genuinely aligns with part of a database item scores high, while coincidental patch matches are discarded. Overlap with the full image is not required.

The print project's own evaluation: on 6 synthetic partial prints, raw matching scored 1/6 top-1; with an LLM-based isolation pre-step, 3/6 top-1. Honest caveat: n=6 is anecdote, not proof — and the isolation step is an OpenAI API dependency that Elastofirm queries (clean drawings/scans, not muddy floor photos) largely won't need.

3 · The one real technical risk

ORB keypoint density on silhouettes

Shoe soles are texture-rich: tread patterns give ORB hundreds of distinctive corners. Elastofirm profile drawings are near-binary silhouettes — large smooth black regions with information only along the contour. ORB on such images finds far fewer, less distinctive keypoints (corners of the cross-section, lip tips, hollow chambers). It may still be plenty — rubber profiles are geometrically intricate — but this is exactly the kind of thing that looks fine in theory and fails on real data.

Mitigations if density is low: run ORB on the Canny edge map instead of gray (the print pipeline already computes it); raise ORB's nfeatures and lower its FAST threshold; or swap ORB for contour-sampled descriptors. All cheap to test.

This is why the recommendation starts with a pilot eval, not an integration.

Why A beats B as the starting point

  • No migration risk: the existing 451 MB index keeps working untouched; stage 2 is additive.
  • It's where the new capability lives: partial matching comes from ORB+RANSAC, not from the bigger global descriptor.
  • It kills the latency problem: ORB is rotation-aware, so the 72-rotation brute force can drop to the 4 cardinal angles (or none) — from 2–15 s towards well under a second, on CPU.
  • Better precision for "doorselecteer"-style work: RANSAC inlier counts give an interpretable "geometrically consistent match" signal the UI could even visualise (the print app draws the matched keypoints).

5 · Proposed shape (option A)

query image→ existing preprocess + HOG + PCA→ cosine vs 12,186 (stage 1)→ top-300 → ORB + RANSAC rescore (stage 2)→ blend + rank→ same API response
  • Decoupling first: introduce a small matcher interface (the audit confirmed the endpoint is hardcoded to ProfileMatcher) and a MATCHER=legacy|hybrid env flag — instant rollback, A/B-able.
  • Index side: extend the index build to also store ORB keypoints/descriptors per profile; the new elastofirm index commands (delta, backup, lock) make the rebuild safe and resumable.
  • API contract unchanged: same endpoint, same response shape (query_rotation becomes the RANSAC angle).

6 · Recommended plan

  1. Pilot eval (1–2 days, go/no-go): offline script on ~50 indexed profiles — generate synthetic partials (40–70% crops, rotated), measure top-1/top-5 for (a) current matcher, (b) ORB+RANSAC prototype. Explicitly measure ORB keypoint counts on profile drawings vs the edge-map variant. Produces real numbers instead of the print project's n=6.
  2. Phase A (if pilot passes): matcher interface + feature flag → ORB store in the index (delta rebuild) → two-stage search → regression suite + eval report. The latency win (dropping the 72-rotation loop) lands here too.
  3. Phase B (optional, data-driven): trial the combined 16k descriptor as stage 1 on the eval set; adopt only if it beats HOG+PCA on profile data. Full guarded reindex.
  4. Product check: confirm with the PO that partial-profile queries are a real workflow (photo of a profile fragment, cropped scan) — worth a Linear issue; this also closes the open question of whether to surface a "partial match" indicator in the UI.
Verdict: incorporate it — as a second-stage rescorer behind the existing index, gated by a 1–2 day pilot on real profile drawings. The architecture transfers cleanly (same CPU/OpenCV stack, importable functions, two-stage design made for exactly this), the payoff is partial-image matching plus a large latency cut, and the only material unknown — ORB keypoint quality on silhouettes — is cheap to measure before committing. Don't port the global embedder or the OpenAI isolation step until the data says so.
