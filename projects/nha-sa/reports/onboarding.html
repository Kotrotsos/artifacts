NHA SA Classification API

A FastAPI service that classifies inbound Dutch customer-service emails for NHA, an education institute, into the right handling category, with a fast guard for welcome-gift questions and a slot extractor for order numbers.

What it is

NHA receives a high volume of customer emails (cancellations, enrolment questions, returns, payment queries, and so on). This service takes the subject and body of an incoming email and returns a single best-fit category so downstream systems can route or auto-respond. It exposes a small, key-authenticated REST API and is built to run on Azure App Service.

Three distinct jobs live behind the API:

Category classification

Maps an email to one of ~193 NHA categories using a hosted LLM deployment (via ORQ.ai). This is the primary product.

Welcome-gift guard

A cheap LLM pre-check that short-circuits "verzilveren welkomstcadeau" questions straight to category 199 before spending a full classification call.

Order-number extraction

A GPT-4 "slot" extractor that pulls a 6-digit order number out of an email and reports its confidence and location.

One-line mental model Email in, category (and optionally an order number) out. Most of the intelligence lives in hosted LLM prompts, not in this codebase. The service is the routing, auth, cleaning, and validation layer around those prompts.

Business context

NHA (Nederlandse Handels Academie) is a Dutch distance-learning institute. The category taxonomy is therefore in Dutch and very domain-specific: enrolment lifecycle, returns and retournering, welcome gifts, payment confirmations, digital learning environment access, and more. The canonical list of categories and the classification instructions live in test_emails/prompt.md (around 193 categories, with id 27 = "Overig" as the catch-all and id 199 = welcome-gift redemption handled by the guard).

An ongoing evaluation effort lives in test_emails/: real exported inboxes (January, February, March 2026), model judgements (judged.csv, judged1000.csv, result.csv), a category-description reference, and an evaluation write-up (NHA_Categorisatie_Evaluatie.docx). This is how classification quality is measured against real mail.

Architecture

A single FastAPI app (main.py, ~1,300 lines) is the whole service surface. It delegates the actual reasoning to external LLM providers and, for one endpoint, to a local prototype classifier.

LayerResponsibilityWhere
API + authRouting, X-API-Key verification, HTML cleaning of email text, request/response models, error handling, the tester UImain.py
LLM category classifierCalls the ORQ.ai-hosted deployment (EMAIL_CAT_01), parses the returned {id, category_name} JSONmain.py → ORQ.ai
GuardCalls the same ORQ deployment in a guard_verzilveren environment that returns PASS/FAILmain.py → ORQ.ai
Order-number slotCalls OpenAI GPT-4 with a specialised extraction prompt, then validates the result is exactly 6 digitsmain.py → OpenAI

Two classifiers, by design The production category path is the LLM one (ORQ.ai). The prototype classifier in classify/ is an earlier embedding-based approach kept for the /response and /train endpoints; its label_cards.json currently ships with a single label (53). Do not assume /category uses it.

External dependencies

ORQ.ai
Hosts the email-category prompt and the welcome-gift guard as a deployment. Invoked over HTTPS with a bearer token (ORQ_API_KEY).
OpenAI
Used for order-number extraction (GPT-4) and, optionally, as the embedding backend for the prototype classifier (text-embedding-3-small).
Azure App Service
Production host. Runs gunicorn + uvicorn workers. Resource group and app name are environment-specific.

All routes are under /api/v1. Every endpoint except status requires the X-API-Key header.

Example call

curl -X POST "http://localhost:8000/api/v1/category" \
  -H "X-API-Key: $SA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
        "subject": "Vraag over mijn inschrijving",
        "body": "Ik wil graag mijn welkomstcadeau verzilveren...",
        "use_subject": true
      }'

Request flow: /api/v1/category

This is the endpoint that ties everything together. Follow it once and the rest of the service is easy to read.

1
AuthenticateVerify the X-API-Key header against the configured keys. Reject with 401 if missing or invalid.
2
Build email summaryStrip HTML tags and entities from subject and body, then combine into a clean text summary.
3
Run the guardCall ORQ.ai in the guard_verzilveren environment. It answers PASS or FAIL.
4
Short-circuit on PASSIf PASS, immediately return {id: 199, category_name: "Vraag over verzilveren welkomstcadeau"}. No full classification needed.
5
Fall back to LLM classifierOn FAIL, call the full ORQ deployment, parse {id, category_name}, and return it with the guard decision and raw generations attached for debugging.

Local setup

Requires Python 3.10 or higher.

# 1. Clone and enter the repo
cd nha-sa

# 2. Create and activate a virtualenv
python3 -m venv venv
source venv/bin/activate

# 3. Install dependencies (full set, includes ML libs)
pip install -r requirements.txt

# 4. Create your .env (see the next section), then run:
uvicorn main:app --host 0.0.0.0 --port 8000 --reload

Then open:

  • API: http://localhost:8000
  • Swagger: http://localhost:8000/api/v1/docs
  • Tester UI: http://localhost:8000/ui/category-tester
Fast first run If you only need the LLM category path, install requirements-azure.txt instead and set USE_OPENAI_EMBEDDINGS=true. You skip the multi-GB PyTorch download and the server starts in seconds.

Secrets hygiene Real API keys and the ORQ token currently appear in some committed helper files (for example notes.txt and parts of the README). Treat any key you find in the repo as compromised: do not reuse it, rotate it, and keep new keys in .env or Azure App Settings only. Never paste live secrets into docs or commits.

Working with categories

There are two places categories live, depending on which classifier you are touching.

LLM classifier (production)

The category list and instructions are the ORQ.ai prompt, mirrored locally in test_emails/prompt.md. To change categories or classification behaviour for the production path, you edit the prompt in ORQ.ai, not this repo. Use the orq tooling / dashboard for that.

Prototype classifier (classify/)

Used by /response and /train. Each category is a "label card" in label_cards.json with a definition, positive examples, exemplars, and negatives. The classifier embeds these into a prototype vector and classifies by cosine similarity against a per-label threshold (tau).

# After editing label_cards.json, rebuild prototypes:
curl -X POST "http://localhost:8000/api/v1/train" -H "X-API-Key: $SA_API_KEY"
# or delete classify/prototypes.pkl and restart (auto-retrains)
Switching embedding backends means retraining Embeddings from OpenAI and HuggingFace are not interchangeable. If you flip USE_OPENAI_EMBEDDINGS, you must retrain or the cosine scores will be meaningless. See classify/README.md and EMBEDDING_SETUP.md.

Testing & evaluation

  • smoke_guard_and_llm.sh — validates the guard + LLM category path against representative emails, local and/or Azure.
  • test_ordernumber.sh — eight cases for the order-number extractor (subject, body, labels, multi-number, none found, hashtags).
  • test_azure.sh, test_api.sh, test.sh — broader endpoint checks.

APP_URLS="http://localhost:8000 https://<app>.azurewebsites.net" ./smoke_guard_and_llm.sh

Load testing

python load_test.py --url https://<app>.azurewebsites.net \
  --key "$SA_API_KEY" --endpoint all -n 100 -c 10

Reports success rate, min/max/mean/median latency, P50/P90/P95/P99, status-code distribution, and throughput.

Quality evaluation

Classification accuracy is assessed against real mail in test_emails/. Monthly inbox exports are run through the classifier, results are recorded in judged.csv / result.csv, and findings are summarised in the evaluation documents. evaluation_chart.html visualises the outcome. This is the source of truth for "how good is the model right now".

Deployment

Production runs on Azure App Service (Linux, Python). The key wrinkle is the requirements swap.

Why two requirements files The full requirements.txt pulls in PyTorch and sentence-transformers (3-4 GB), which times out Azure builds. Production uses only OpenAI embeddings, so it does not need them. deploy.sh automatically backs up the full file, swaps in requirements-azure.txt, deploys, and restores the original for local use.

Deploy

./deploy.sh        # handles requirements swap, packaging, zip-deploy, restart

What Azure needs configured

  • Startup command: gunicorn -w 4 -k uvicorn.workers.UvicornWorker main:app --bind=0.0.0.0:8000 (see startup.sh).
  • Build on deploy: SCM_DO_BUILD_DURING_DEPLOYMENT=true must be set, or you get ModuleNotFoundError. This is the single most common deploy failure.
  • App settings: SA_API_KEY, ORQ_API_KEY, OPENAI_API_KEY, USE_OPENAI_EMBEDDINGS=true.

Provisioning a fresh web app is scripted in create_webapp.sh. Detailed guidance, including quota notes, is in AZURE_DEPLOYMENT.md and AZURE_QUOTA.md.

Verify after deploy

curl https://<app>.azurewebsites.net/api/v1/status
az webapp log tail --name <app> --resource-group <rg>   # stream logs
SymptomLikely cause

Day-to-day developer workflow

  1. Branch off main (the team works on feature branches such as ui).
  2. Run locally with --reload and exercise changes through the tester UI or curl.
  3. Run the relevant smoke script before pushing anything that touches classification.
  4. Commit with a clear, concise message. Commit after each meaningful change.
  5. Deploy with ./deploy.sh, then verify /api/v1/status and tail logs.
  6. For prompt or category changes, edit in ORQ.ai and re-run evaluation against test_emails/.

Day-one checklist

  • Clone the repo and create a Python 3.10+ virtualenv.
  • Get an SA_API_KEY, an ORQ_API_KEY, and an OPENAI_API_KEY from the team (do not reuse keys found in the repo).
  • Create .env from .env.example and fill in the keys.
  • Install dependencies and start the server with uvicorn main:app --reload.
  • Hit /api/v1/status and open /api/v1/docs to confirm the app is up.
  • Run a classification through /ui/category-tester and watch the guard decision.
  • Read README.md, classify/README.md, and SLOT_EXTRACTION.md end to end.
  • Open test_emails/prompt.md to see the full category taxonomy.
  • Run smoke_guard_and_llm.sh against local to confirm the LLM path works.
  • Skim AZURE_DEPLOYMENT.md so the deploy story is not a surprise later.
