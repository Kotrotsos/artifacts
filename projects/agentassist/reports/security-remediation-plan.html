Security remediation plan

Six findings from the audit, ordered by leverage. The chat endpoint stays public on purpose; abuse is bounded with layered controls, not authentication.

Guiding constraint. agentassist is a public-facing chatbot. The chat endpoint has to be reachable without login from any visitor. So "fix" for that endpoint is not authentication, it is making abuse expensive: origin pinning, multi-tier rate limits, per-tenant token budgets, concurrent-stream caps, and an optional bot challenge. Everything else (session ids, CSP, error sanitization, admin per-tenant passwords, the key rotation) is straightforward.

Order of operations

Top of the list is highest leverage per minute of work. Items 1 and 2 should ship together as the first PR.

  1. Rotate the leaked Anthropic key. Manual, 5 minutes, zero code. Cleans up the existing leak before anything else lands. (Fix 3 below.)
  2. Server-issued session ids + abuse controls + CSP + error sanitization. One coherent PR. Touches app.py, auth.py, tenants.py, the frontend. About a day of work. (Fixes 1, 2, 4, 5.)
  3. Per-tenant admin passwords. Standalone, ~half a day. Defer until after OSS launch unless you need it sooner. (Fix 6.)

1. Chat endpoint: abuse controls, not authentication

P1~1 day

Goal

Make it costly to abuse the public chat endpoint without making it inaccessible to legitimate visitors. Five layered defenses, each cheap on its own.

Design

Layer A. Origin pinning per tenant. Each tenant gets an allowedOrigins field (list of host strings, optional). When set, POST /api/{tenant}/chat rejects requests whose Origin header is not on the list, returning 403. Empty list means "no origin check" (the open default for the demo and for OSS users who haven't configured it). Stops casual scrapers from pointing their script at your URL.

Layer B. Multi-tier rate limits. Today there is one limit (per IP per minute). Add three more so an attacker can't shrug it off by rotating IPs:

  • Per IP per minute: 20 (existing).
  • Per IP per hour: 200 (new, soaks IP rotation).
  • Per session per minute: 10 (new, since sessions become server-issued in Fix 2).
  • Per tenant per minute: 200 (new, global ceiling so one tenant's abuse can't starve another's traffic).

All four limiters use the existing RateLimiter sliding-window primitive. No new dependency.

Layer C. Per-tenant token budget. Each tenant has a daily input + output token budget (configurable, default e.g. 200K tokens). The agent records actual usage from response.usage after each turn and accumulates per-tenant in a JSONL file (one line per turn: {tenant, session, ts, in, out}). When the rolling 24-hour total crosses the budget, return a friendly 503 with a "service paused" message and a Retry-After header set to the next reset. Cap your worst-case Anthropic spend predictably.

Layer D. Concurrent-stream cap per IP and per tenant. A semaphore-style counter that increments before iter_turn and decrements on exit (or on disconnect). Defaults: 2 concurrent streams per IP, 20 per tenant. Blocks the trivial "open 100 connections" pattern.

Layer E. Optional bot challenge. Wire up Cloudflare Turnstile or hCaptcha as an opt-in via BOT_CHALLENGE=turnstile env var. Frontend embeds the challenge widget on the welcome screen; first chat request includes the challenge token; backend verifies it server-to-server. Off by default for OSS demo; documented for production deployments.

Code touch points

  • tenants.py: add allowedOrigins: list[str], dailyTokenBudget: int to Tenant.
  • app.py: new helper _check_origin(tenant); expand _rate_limit calls in api_chat to all four tiers; new UsageLedger reading/writing tenants/{id}/usage.jsonl; concurrent-stream context manager around iter_turn.
  • agent.py: after stream completes, call ledger.record(tenant_id, session_id, response.usage).
  • static/admin.html: editor fields for allowedOrigins and dailyTokenBudget.
  • (Optional) app.py: _verify_bot_challenge(token) helper, fetches Turnstile's verify URL.

Tests

  • tests/test_routes.py: chat with disallowed origin returns 403.
  • tests/test_routes.py: rate-limit per IP per hour blocks the 201st request.
  • tests/test_ratelimit.py: tenant-wide bucket independent of IP bucket.
  • tests/test_app.py: usage ledger writes tenants/{id}/usage.jsonl after a turn, daily budget enforcement blocks 503 once exceeded.
  • Concurrent-stream cap: spawn 3 threads, third gets 429 / 503.

Trade-offs

  • Token budget needs persistence to survive restarts. JSONL on local disk is fine for one Railway instance; document Redis for multi-instance.
  • Turnstile makes the demo less friendly. Keep it strictly opt-in.
  • Origin pinning breaks server-to-server callers; document that pattern as "leave allowedOrigins empty or include the calling host".

2. Server-issued session ids

P1~2-3 hours

Goal

The browser never picks its own session id. Every session is an opaque, unguessable, HMAC-signed token issued by the server, bound to a tenant, with an expiry.

Design

Reuse auth.make_token / verify_token (we already use HMAC for admin). New helper:

def make_session_token(tenant_id: str) -> str:
    sid = secrets.token_urlsafe(16)
    return make_token({"t": tenant_id, "sid": sid}, ADMIN_SECRET, ttl_seconds=24*3600)

Two issuance paths:

  • Same-origin (full-screen mode): GET /api/{tenant}/config sets a cookie aa_session=<token> with HttpOnly; Secure; SameSite=Lax; Path=/api/{tenant}/ if not already present.
  • Cross-origin (embed widget mode, future): the same config endpoint returns the token in the JSON body so the widget can store it client-side. Cookies don't reliably work in third-party iframes; the body path is the workaround.

On every chat / reset request:

  • Resolve token from cookie OR Authorization: Session <token> header.
  • Verify HMAC + expiry + that claims["t"] == tenant_id. Mismatch returns 401.
  • Pass claims["sid"] down as the session key to agent.iter_turn. Reject any session_key in the request body.

Code touch points

  • auth.py: add make_session_token, verify_session_token(tok, tenant_id).
  • app.py: new helper _resolve_session(tenant); remove all reads of data["session_key"] from chat / reset endpoints; set cookie on /api/{tenant}/config; include token in config JSON for widget mode.
  • static/index.html: drop sessionStorage logic; read token from /api/{tenant}/config response and pass it via Authorization header on subsequent chat calls.

Tests

  • Chat without a valid session token returns 401.
  • Chat with a token issued for a different tenant returns 401.
  • Reset works with a valid token; rejected without.
  • Cookie is set on config GET and not on subsequent requests.
  • Expired token returns 401 with a clear reason.

Trade-offs

  • Existing in-flight sessions break on deploy. Acceptable for an alpha; mention in the release note.
  • For cross-origin embedding later, the token-in-body path bypasses cookie issues but requires the widget to keep the token in sessionStorage (still server-signed, still unforgeable).

3. Rotate the Anthropic API key

P15 minutes, manual

Procedure

  1. Open https://console.anthropic.com/settings/keys and create a new API key with the same workspace + permissions as the current one.
  2. Run: railway variables --service agentassist --set "ANTHROPIC_API_KEY=<new-key>". Railway redeploys automatically.
  3. Smoke-test: curl -sS -N -X POST "$URL/api/montferland/chat" -d ... | head -5 should still stream.
  4. Revoke the old key in the Anthropic console.
  5. Overwrite the local .env with the new value (or delete it entirely; the deploy uses Railway env vars).

Permanent runbook

Add docs/SECURITY.md with a "Rotating ANTHROPIC_API_KEY" section. Frequency: at least every 90 days, plus immediately on any suspected leak. Document the same procedure for ADMIN_PASSWORD and ADMIN_SECRET.

Note

If you want to scrub the literal key from this conversation's transcript before any of it is archived elsewhere, do that step before rotating. Once rotated, the leaked value is dead, but cleaning the transcript prevents future confusion.

4. Content-Security-Policy + frame protection

P2~1 hour

Design

Single after_request change in app.py. Use one CSP for app routes, a separate (looser) CSP for the future embed-widget bundle if it ever ships.

CSP = (
  "default-src 'self'; "
  "connect-src 'self'; "
  "img-src 'self' data:; "
  "style-src 'self' 'unsafe-inline'; "
  "script-src 'self' 'unsafe-inline'; "
  "base-uri 'none'; "
  "form-action 'self'; "
  "frame-ancestors 'none'"
)
resp.headers.setdefault("Content-Security-Policy", CSP)
resp.headers.setdefault("X-Frame-Options", "DENY")
resp.headers.setdefault("Permissions-Policy",
    "geolocation=(), microphone=(), camera=(), payment=()")

Why 'unsafe-inline'. Inline <style> and <script> blocks in the static HTML are how we keep the app dependency-free. A nonce-based CSP would require server-side templating to inject a per-response nonce, which contradicts the "ship static HTML, edit-and-refresh" workflow. Acceptable trade-off documented in docs/SECURITY.md.

Tests

  • Every HTML response carries CSP, X-Frame-Options, Permissions-Policy headers.
  • API responses do as well (since fetch could be mounted in an iframe).

Follow-up

If the project ever ships a third-party-embeddable widget bundle, give the bundle its own route (/widget.js) and serve it with a relaxed CSP that allows the iframe parent. Do not relax the main app's CSP.

5. Sanitize error messages

P2~30 minutes

Design

Two changes:

  1. Generic fallback in agent.friendly_error. Replace the current return f"{type(e).__name__}" with a static "Er ging iets mis. Probeer het zo opnieuw." Log the full exception (with request id) server-side via log.exception(...).
  2. Generic _err_response in app.py. Today the body includes err.description verbatim. Most callers pass a known-good string, but it's load-bearing to keep it that way. Add a guard: never echo strings that contain Traceback, at line, file paths, or anything matching a heuristic "looks like a stack trace" check. Always include a server-generated request_id in the response body so support can correlate.

Code touch points

  • agent.py:friendly_error + iter_turn error path.
  • app.py:_err_response + each errorhandler wraps the description in a safe formatter.
  • app.py request middleware: generate g.request_id = secrets.token_hex(8); attach to log records; return in X-Request-ID header.

Tests

  • Inject a non-transient exception (e.g. a fake RuntimeError("filesystem path /etc/...")); confirm the streamed error event contains the generic message, not the path.
  • Confirm every response carries X-Request-ID.
  • Confirm server logs include the full exception when sanitization happens.

6. Per-tenant admin passwords

P2~half a day

Goal

Two roles: a super-admin who manages the platform (creates tenants, sets per-tenant passwords) and per-tenant editors who can only manage their own tenant. Same flow as the spec describes (ADMIN-1 open point).

Design

Storage. Add passwordHash: str | None to Tenant config. Hash with argon2id (single-file dependency, pip install argon2-cffi). Empty hash means "no per-tenant password set; only super-admin can manage this tenant".

Endpoints.

  • POST /api/admin/login accepts { password } (super-admin) or { tenant_id, password } (tenant-scoped). Body shape disambiguates.
  • Token claims include role: "super" | "tenant" and tenant_id?.
  • Existing admin routes check claims: tenant-scoped tokens can only operate on their own tenant id; super-admin tokens can access anything.

Admin UI. A "set tenant password" field in the editor, visible only when logged in as super-admin. Hash-and-save flow.

Code touch points

  • tenants.py: new passwordHash field; set_password(tenant_id, password) + verify_password(tenant_id, password) helpers using argon2.
  • auth.py: make_token already accepts arbitrary claims; just add role + tenant_id.
  • app.py:_require_admin: support tenant-scoped tokens; new _require_admin_for(tenant_id) that checks both super-admin and matching tenant-scope.
  • static/admin.html: tenant password field; UI branches by role; tenant list filtered for tenant-scoped users.
  • requirements.txt: add argon2-cffi>=23.1.0.

Tests

  • Tenant-scoped token cannot read or write a different tenant's config.
  • Super-admin can set a per-tenant password; subsequent tenant-scoped login with that password works.
  • argon2 hash round-trip; old hashes still verify after a parameter bump.
  • Login rate limit still applies to per-tenant logins.

Stretch

  • Optional: lockout / progressive backoff after N failed tenant-scoped logins.
  • Optional: password reset via super-admin-only endpoint.

OSS recommendation

Ship the simple single-password model for v1 OSS release. Add this feature in v0.2 with a CHANGELOG note. It is a real feature, not a security gap, and adding it before launch slows down the release with no urgent benefit (single-operator deployments are common).

What we are explicitly not doing

  • Locking down the chat endpoint with auth. Public chatbots must accept anonymous visitors. The "fix" is making abuse expensive, not impossible.
  • Adding a WAF or DDoS service. Railway already fronts the service. Cloudflare in front is one DNS change away if needed; not in scope for the code base.
  • Encrypting tenant config at rest. Filesystem-only storage on Railway is already private to the service; encryption adds key management overhead without changing the threat model.
  • Implementing markdown rendering or feedback collection. Mentioned earlier as nice-to-haves; not part of the security plan.
