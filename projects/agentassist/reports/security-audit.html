Security audit and comparison

Concrete findings against each project, with file:line references, severity, and recommended fix. Severity uses P1 (must fix before any exposure), P2 (should fix soon), P3 (nice-to-have).

Headline. Both projects have real P1 issues. virtuele-assistent's are mostly weak defaults baked into shared infrastructure (compose, Airflow, admin DB); agentassist's are mostly absent controls on a small surface area (no auth on the chat endpoint, client-controlled session keys). Neither is yet "ship to the internet" ready, but agentassist needs less work to get there because its attack surface is smaller.

1Scorecards

agentassist

B-
Small attack surface, server-side PII redaction in pipeline, host-allowlisted web_fetch, rate-limited, no DB to compromise. Open gaps: chat endpoint is unauthenticated, session_key is fully client-controlled, no CSP, an API key was at one point written to the local .env before .gitignore existed.

virtuele-assistent

C
Strong server-side PII service, X-API-Key between services, real RAG inside a closed network, nginx rate-limit on chat. Open gaps: weak default secrets in docker-compose.yml ("changeme", "adminpass123", "super-secret-key-change-me", literal "airflow"), one hardcoded Postgres password, anyHost() CORS, no CSP / security headers in nginx, Qdrant published on host port 6333, very large secret surface (Langfuse, OpenAI, Azure OpenAI, Airflow Fernet, Airflow secret, two admin passwords, DB password).

2Findings: agentassist

P1Chat endpoint is unauthenticated
app.py: POST /api/{tenant}/chat

Anyone reachable can spend Anthropic credits. The only abuse control is a 20/min/IP rate limit, which a determined attacker rotates IPs around. Fix: require a signed visitor token, a shared header issued by your web property, or keep the deploy behind a private network.

P1session_key is client-controlled
app.py + static/index.html

Any tab can pass any session key and read, poison, or reset another visitor's history. Fix: issue server-side opaque ids in a signed cookie, reject arbitrary keys. Acceptable for localhost demos; not acceptable for the public URL.

P1API key was committed to .env before .gitignore existed
earlier in this session's conversation history

The current .gitignore protects .env, but the literal Anthropic key was written to the file before that. It is also stored as a Railway service variable now. Rotate the key in console.anthropic.com, update Railway, revoke the old one.

P2No Content-Security-Policy header
app.py:register_after_request

The app sets X-Content-Type-Options and Referrer-Policy but not CSP. Recommended baseline: default-src 'self'; connect-src 'self'; base-uri 'none'; frame-ancestors 'none'. Inline <style> in index.html needs either 'unsafe-inline' (acceptable trade-off for this app) or a nonce.

P2Error text from upstream may bleed to the client
agent.py:friendly_error

Friendly messages exist for the common cases (overloaded_error, rate_limit_error, timeout), but anything outside the known set falls back to type(e).__name__. Acceptable, but resist passing str(e) from third-party libraries downstream.

P2Single global admin password
app.py:admin_login

One password controls every tenant in admin. For an OSS template this is OK as the default, but document per-tenant credentials as a future extension. Spec ADMIN-1 already flags this.

P3In-memory state has no TTL
agent.py:_histories

Long-lived processes accumulate per-session conversation histories. Bound it by either a max-size LRU or a time-to-live (e.g. 1 hour idle). Memory growth, not security, but worth flagging.

P3CORS defaults to wildcard
app.py + ALLOWED_ORIGINS env

ALLOWED_ORIGINS=* is the default. Fine for a local demo, but when the chat is embedded as a widget, set this to the exact host site(s).

What is already right. Server-side PII redaction runs before the message reaches the model or logs. web_fetch is locked to a per-tenant allowlist with max_uses=3 (prompt injection cannot redirect it). Tenant ids are regex-validated, blocking path traversal. Body size is capped at 64 KB. Per-session lock prevents history races. Frontend uses textContent everywhere; no innerHTML with user content.

3Findings: virtuele-assistent

P1Weak default secrets baked into compose
docker-compose.yml:15-16, :91, :125, :172, :200

The compose file ships with usable defaults: AIRFLOW__API__SECRET_KEY:-super-secret-key-change-me, POSTGRES_PASSWORD:-adminpass123, ADMIN_PASSWORD:-changeme, and a hardcoded literal POSTGRES_PASSWORD: airflow on the Airflow postgres (no env var indirection). Any environment that skipped a .env step deploys with these. Fix: change every ${VAR:-default} to ${VAR:?error} so missing values fail fast, and remove the literal "airflow" password.

P1CORS is wide open on the backend
agent-backend/src/main/kotlin/Application.kt:92-99

install(CORS) { ... anyHost() }. Any origin can make authenticated cross-site requests once a session cookie or token is involved. Fix: list explicit allowed hosts, mirror the production frontend origin only.

P1Qdrant is published on host port 6333
docker-compose.yml:73   - "6333:6333"

On a docker host with a public interface, Qdrant is reachable without auth. Fix: drop the host port mapping, keep it on the internal Docker network only; if external access is needed, terminate behind a reverse proxy with auth.

P2No security headers in nginx
nginx.conf

No CSP, no X-Content-Type-Options, no Referrer-Policy, no X-Frame-Options. Fix: add_header directives on each location, or a top-level map block. CSP for an embeddable widget needs care; do an explicit allowlist for the host pages.

P2No TLS termination configured
nginx.conf + compose

The nginx config is port 80 only. Behind a managed platform (Cloud Run, an upstream load balancer with TLS), this is acceptable. For Helm production, add the TLS-terminating ingress and HSTS.

P2Large secret surface
.env.example

Required for production: Langfuse (public + secret), OpenAI, Azure OpenAI (key + endpoint + version), Airflow Fernet, Airflow secret, admin pass, admin DB pass, and the inter-service API key. That is many places to leak from and many places to rotate. Document a rotation runbook; consider a secrets manager (AWS SSM, Doppler, Vault) so this is not all in .env files.

P2Single global admin password
docker-compose.yml:172 + admin backend

Same issue as agentassist, called out in the project's own spec as an open point. Per-tenant credentials should be the eventual fix.

P3Frontend-mediated PII redaction has a fallback
spec PII-2, agent-frontend/components/civai/assistant-bubble.tsx:23

Spec says: "Bij redact-fail (404, timeout): fallback naar raw body met error in console; verzoek breekt niet." That is a usability-vs-privacy trade-off; in worst case raw PII reaches the model and Langfuse traces. The backend also runs PII redaction (defense in depth), so this is P3 rather than P2.

What is already right. Server-side PII redaction is its own Kotlin service (132 LOC, 6 patterns, including BSN elfproef), invoked on every chat request. X-API-Key between frontend and backend short-circuits unauthenticated calls. nginx rate-limits /ai/ to 10 req/sec/IP with burst 20. .gitignore covers .env. The Airflow stack and Postgres are on a private Docker network. Per-tenant Qdrant collections prevent cross-tenant data leakage at the retrieval layer.

5Before either goes to a public URL

agentassist: the four blockers

  1. Rotate the Anthropic key. The literal value sat in the local .env earlier and in this conversation log. Generate a new one in console.anthropic.com, set it on Railway, revoke the old.
  2. Authenticate the chat endpoint. Either bind the service to a private network, require a shared secret header, or issue a signed visitor cookie. Pick one before exposing the URL.
  3. Server-issue session ids. Replace the client-supplied session_key with an opaque server id stored in a signed cookie. Reject anything else.
  4. Add a CSP header. A baseline (default-src 'self'; connect-src 'self'; base-uri 'none'; frame-ancestors 'none') closes the easy XSS / clickjacking paths.

virtuele-assistent: the three blockers

  1. Eliminate every default secret. Replace ${VAR:-foo} with ${VAR:?error} across docker-compose; remove the literal POSTGRES_PASSWORD: airflow; require Fernet + secret + admin pass + DB pass to be set explicitly.
  2. Restrict CORS. Replace anyHost() with the production frontend origin(s). Add an after hook for security headers (CSP, X-Content-Type-Options, Referrer-Policy, X-Frame-Options).
  3. Drop the Qdrant host port mapping. Qdrant is an internal service; do not expose port 6333 on the docker host. If external admin access is required, terminate behind authenticated reverse proxy.

6For an OSS release, who is safer to publish?

An OSS release ships with whatever defaults you put in the repo. People will deploy it as-is.

  • agentassist: smaller blast radius if someone deploys it carelessly. The only running process is one Flask app; there is no exposed datastore, no scheduler, no Airflow worker. A bad deploy costs the operator some Anthropic credits, not exfiltration of a database.
  • virtuele-assistent: a careless deploy gives an attacker the admin DB password, Postgres credentials, and Qdrant access. The "changeme" defaults are dangerous specifically because they are usable as-is.

This is another reason agentassist is the better OSS candidate: the worst case of a misuse is bounded. The pre-OSS checklist should still include the four blockers above plus a SECURITY.md with a clear statement of what the project does and does not protect against (no DDoS protection, no PII redaction completeness guarantee, etc.).
