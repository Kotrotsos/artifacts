2New findings introduced by the remediation work

Two minor things turned up while reading the changes. Neither is a regression of an existing protection, both are small additions that became visible because the rest got tighter.

P3/api/{tenant}/redact still exposed and unrate-limited
app.py:api_redact

The frontend no longer calls this endpoint (redaction happens inside api_chat). It is still mounted and returns the same redacted output plus counts. An attacker could use it as a black-box oracle to probe which patterns the server matches (e.g., test variant BSN spacings).

Fix: either remove the route entirely (recommended, since nothing calls it) or apply a rate limit (e.g., 20/min/IP).

Live probe just now: POST /api/montferland/redact returned 200 with no auth, no rate limit.

P3SESSION_SECRET not set explicitly on Railway
app.py env wiring

Live env check shows ADMIN_SECRET is set but SESSION_SECRET is not. Today this is harmless: SESSION_SECRET falls back to ADMIN_SECRET at startup (SESSION_SECRET = os.environ.get("SESSION_SECRET") or ADMIN_SECRET), so sessions persist across restarts as long as ADMIN_SECRET doesn't change.

The risk is operational: if someone rotates ADMIN_SECRET (good admin hygiene), every visitor's session token also gets invalidated. Setting SESSION_SECRET independently breaks the coupling so the two can rotate on different cadences.

Fix:

railway variables --service agentassist \
  --set "SESSION_SECRET=$(python3 -c 'import secrets;print(secrets.token_hex(32))')"

3Fresh look at the new code

Spot-checked every module that changed or was added.

Session tokens (auth.py)

  • HMAC-SHA256 with hmac.compare_digest for sig comparison: not timing-leaky.
  • Token claims are {t: tenant_id, sid: random16Bytes_base64url, exp: unix_ts}. Body is base64'd JSON, not encrypted. Nothing sensitive in the claims; the sid is opaque random.
  • Tenant binding enforced: verify_session_token returns None if claims["t"] doesn't match the tenant id from the URL.
  • Cookie attrs verified on production response: Secure, HttpOnly, SameSite=Lax, path-scoped per tenant, 24h expiry.

Markdown renderer (static/index.html MD module)

  • Builds DOM via createElement + textContent only. No innerHTML. Model output cannot inject HTML.
  • Link URLs filtered: new URL(url, window.location.origin) then protocol allowlist (http:, https:, mailto:). javascript: and data: URLs render as plain text.
  • Inline regex uses lazy quantifiers + negated character classes, no nested unbounded quantifiers, no catastrophic backtracking risk.
  • Link text and code content are set via textContent: even if the model emits [<script>](javascript:...) nothing executes.

Budget ledger (budget.py)

  • JSONL file per tenant. Append-only writes under per-tenant lock. Reads are O(file size); at the default 200K tokens/day budget that's hundreds of bytes per day per tenant.
  • File path uses the regex-validated tenant id from tenants.py: no path traversal.
  • tokens_last_24h tolerates malformed JSON lines (skips them); no parse-error crash path.

Concurrency cap (concurrency.py)

  • Counter dict guarded by a single Lock. Acquire / release pair around the SSE generator; finally-block in app.py ensures release even on disconnect.
  • Per-worker only. If you ever scale to multiple gunicorn workers or instances, the cap becomes per-worker, not global. Document for production.

Origin pinning (app.py:_origin_allowed)

  • Empty allowlist = open (right default for OSS demo).
  • Absent Origin = allowed (server-to-server, curl, same-origin form post).
  • Hostname extracted with urlparse(...).hostname and lowercased; allowlist compared case-insensitively.
  • Defeats casual cross-site scraping from a browser, not curl. Documented trade-off; pair with the rate limits.

Rate limiters (ratelimit.py)

  • Sliding-window deques per key. Working as designed.
  • Bucket dict is not pruned. With many unique IPs, memory grows. Same caveat as the histories dict; flag for long-running deployments.

5Outstanding work

In rough order of "what to do next."

  1. Rotate the Anthropic API key. Operator step. Documented in the deploy notes. No code change required.
  2. Set SESSION_SECRET as its own Railway variable. 30 seconds; decouples session lifetime from admin token lifetime.
  3. Decide on /api/{tenant}/redact. Either remove the route (no callers in the current frontend) or add a rate limit. Removing is cleaner.
  4. OSS release prep. Add SECURITY.md documenting: the threat model, the documented trade-offs (unsafe-inline CSP, wildcard CORS default, single admin password), the things this project does and does not protect against (e.g. no DDoS), how to report a vulnerability.
  5. Per-tenant admin passwords (v0.2). Already planned; not a regression of any previous protection.
  6. Bucket / lock / history TTL. One periodic-prune helper covers all three. Add when you see real-world memory growth, not before.
Verdict. The remediation moved the project from "small but with real holes" to "small with documented trade-offs." The chat endpoint is now legitimately defensible as a public surface: no auth (intended), four independent abuse layers, a hard per-tenant token budget, and CSP+frame protection on every response. Two operator actions remain: rotate the leaked key, and set SESSION_SECRET. After those, the project is ready for OSS release with a SECURITY.md.
