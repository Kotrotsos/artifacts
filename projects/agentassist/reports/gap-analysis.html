Gap analysis: agentassist and virtuele-assistent

Where each project sits relative to a complete multi-tenant chatbot, and what would close each gap. Priorities: Must (block release / production), Should (close before scale), Nice (later).

0What "complete" means here

A complete deployment of a public-facing multi-tenant chatbot, in the spirit of the Montferland spec, covers ten categories. The scoring below is against this target. "Full" means the capability is present and production-shaped; "Partial" means it is present but reduced; "None" means absent; "n/a" means out of scope for that project's design philosophy.

  • Core chat experience
  • Bubble / widget mode
  • Multi-tenant architecture
  • Admin and configurability
  • Knowledge retrieval
  • Tooling and external calls
  • Security
  • PII and privacy
  • Observability and analytics
  • Operational maturity
  • Accessibility
  • OSS / distributability

4The biggest single gap per project

agentassist

The biggest gap is OSS readiness. The product itself is solid (security, a11y, multi-tenant, streaming, markdown, admin all in place), but the repo today is missing a license, README, SECURITY.md, and CI. Without those four files, the project is not actually distributable, regardless of how good the code is. Two-to-three hours of work would change that.

The second-biggest gap is provider abstraction. Bound directly to Anthropic. For an OSS template this is a friction point for evaluators who want to try with their own provider. A small LLMProvider interface keeps Anthropic as the default while letting contributors plug others.

virtuele-assistent

The biggest gap is shipped configuration safety. The product itself is feature-complete (real RAG, admin dashboard, Langfuse analytics, multi-tenant, scheduled ingestion), but the deploy posture is fragile: weak default secrets in compose, Qdrant on host ports, anyHost CORS, no security headers. A careless deploy gives an attacker the keys to the admin DB and the vector store. Roughly a day of work would close all of it.

The second-biggest gap is per-tenant cost controls. Today there is no enforced token / spend ceiling per tenant. For an enterprise system that should be an operational surprise rather than an unsolved problem.

5Cross-cutting observations

  • The two projects are inverses on configuration safety. agentassist fails closed (missing env vars stop the app); virtuele-assistent fails open (missing env vars deploy with usable weak defaults). The difference is one design choice, not effort.
  • Both projects have the same admin-password gap. Each is single-password; each spec already lists this as an open point. Same fix shape on each side (argon2 hash per tenant + role-bound token claims).
  • Each project has one thing the other lacks at the retrieval layer. agentassist has live web_fetch with an allowlist (fresh information, no ingestion); virtuele-assistent has real RAG with hybrid + HyDE + reranker (large knowledge bases, no live data). The most capable solution would combine both: RAG for breadth, allowlisted web_fetch for currency.
  • Observability is the largest functional asymmetry. virtuele-assistent has Langfuse + BSAT + analytics dashboards; agentassist has request id + structured log + JSONL token ledger. For a project owner who wants conversation analytics, agentassist needs an explicit observability story (export traces to Langfuse, or a small built-in analytics page).
  • Tests favor agentassist for iteration speed. 91 tests in < 3 seconds with no external dependencies vs ~830 LOC Kotlin tests that need container fixtures. Both are fine; agentassist's setup encourages tighter iteration.

6Suggested next 30 / 60 / 90 days

agentassist roadmap to v1 OSS

  • Week 1. Rotate Anthropic key. Add LICENSE, README, SECURITY.md, CONTRIBUTING.md. GitHub Actions for pytest. Remove the unused redact route. Set SESSION_SECRET on Railway.
  • Week 2. Provider abstraction (LLMProvider). Draft / publish flow in admin. Prompt-preview endpoint. Per-message feedback (thumbs up/down to JSONL).
  • Week 3. Memory TTL helper. Per-tenant admin passwords. Generalized org-type defaults for non-Dutch deployments. Vector-store extension point + one example adapter.
  • Week 4. docker-compose for local dev with optional Redis. Documentation pass. v1.0 OSS release.

virtuele-assistent hardening sprint

  • Week 1. Compose fail-closed secrets. CORS lockdown. Drop Qdrant host ports. nginx security headers. Fix ingestion restart loop.
  • Week 2. Per-tenant token / cost budget service (mirrors agentassist pattern). Concurrent-stream cap. Secrets-manager runbook.
  • Week 3. Per-tenant admin passwords. Frontend PII fail-closed option. Reranker observability.
  • Week 4. Widget build artifact in CI. Move aria-additions to civai/. Documented TLS termination path.
Bottom line. Neither project has an architectural gap that requires a rewrite. agentassist's gaps are mostly "missing OSS metadata + provider abstraction + a few admin niceties" — under a month of work to v1 OSS. virtuele-assistent's gaps are mostly "shipped-config hygiene + cost controls" — under a month of focused hardening to a defensible production posture. Both lists fit in a single sprint.
