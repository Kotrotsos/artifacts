A trifecta on Anthropic's memory primitive

Memory, dreams, and the next primitive

Anthropic's product team has been incrementally adding capabilities that let agents do more on their own. The newest one is memory, and there is a second piece behind it called dreaming. A read on what shipped, why it matters, and what it changes, in three acts.

Based on a talk by Mahes, product manager on Anthropic's platform team.

Act IThe trajectory

Look at the way Anthropic has shipped over the past two years and you can read it as one long argument. Each release lets the model do more without being told. The Model Context Protocol gave agents a standard way to reach external tools and data. Harnesses like Claude Code and the Agent SDK gave them long-running environments to live inside. Skills, launched in October, gave them a way to pick up new capabilities packaged by other agents or by humans. Each one is a layer that gets out of the model's way and hands it more of its environment to manage.

The thing that the trajectory has not solved, at least until now, is continuous self-learning. Once a session ends, what an agent figured out goes away. The next agent in the same environment has to relearn the same lessons. The same mistakes get made twice. The same investigation runs twice. The strategies that worked last week sit nowhere a future agent can find them.

Memory is the next primitive. It is the thing that will get us to self-learning agents that evolve and improve based on the tasks they work on and their own experience.

The framing matters because memory is not new in casual usage. CLAUDE.md shipped with Claude Code well over a year ago, and the memory tool surfaced in the SDK shortly after, both early versions where an agent could leave itself a note inside a file or call a strictly-typed tool. The new framing is broader. Anthropic now wants memory to cover three things at once:

  • Learning about the task. What does success look like for this work, what are the common mistakes, what strategies have been tried.
  • Learning about the environment. The code base, the files, the assets, the things that move and need to stay current.
  • Learning from other agents. Sharing observations across a fleet. Picking up what is going wrong elsewhere in the system and folding it into the agent's own model of the world.

That last one is the bet that matters. The interesting near future is not a single Claude session per developer. It is hundreds or thousands of agents in the same environment, doing related work, building up a shared understanding nobody planned in advance. For that to be possible, memory has to be a real subsystem with its own design, not a notes file.

Early customer signal backs the bet. One team building internal knowledge agents on top of the new system reported a 90 percent reduction in first-pass mistakes after agents started catching errors and writing them into memory for the next iteration to read. The token cost dropped, the latency dropped, the answers improved. Three wins from the same change, which is the shape of a useful primitive.

Act IIThe architecture

Anthropic's design of memory in Cloud Managed Agents is shaped by four requirements, all of them learned from customers who tried earlier versions. Each one is the kind of constraint that sounds obvious once stated and then quietly drives the entire system.

One: maximize intelligence by default

The temptation with memory is to over-specify the interface. Define exact tool calls, exact parameters, exact output shapes. Anthropic went the other direction. Memory is modeled as a file system. Claude reads and writes files, organizes them into a hierarchy, picks formats it likes. The tools are the same bash and edit primitives that already make the model good at agentic coding. The latest models, particularly Claude Opus 4.7, were specifically tuned for filesystem-based memory, which means they are better at picking what is worth remembering, how many files to split it into, and how to keep the structure organized over time.

The product principle is consistent with what shipped earlier in Skills. If the model is already capable of managing a virtual file system, hand it the memory store and step back.

Two: scale with multi-agent systems

Single-agent memory is easy. Concurrent agents touching the same store is where the design gets serious. Two properties fall out of taking this seriously:

  • Permission scopes. An agent might have read-only access to one store (an organisation-wide runbook, a set of best practices) and read-write access to another (its own working memory). The scoping is per agent per store, which is the only way to keep shared knowledge from getting clobbered while still letting agents write where they should.
  • Optimistic concurrency. When hundreds of agents share memory state, one agent's write should not blindly overwrite another's. Memory updates use a content hash as a precondition, the same pattern any compare-and-swap system uses, so an agent verifies the state it thought it was editing before its write lands.

Three: developer and enterprise control

Production deployments need explainability. The system gives every memory store full version history, attribution metadata for every change (which agent, at what time, from which session), and a portable API that can be reached from outside the managed-agents harness. That last one matters for the customers who already run their own PII scanners, their own cleanup pipelines, their own external mirrors. Memory is not a black box you can only operate through Anthropic's console.

Four: three layers, not one

Anthropic frames the system as three layers, and the framing is useful because it separates concerns that get conflated in casual conversation:

  • Storage. Where the data actually lives, what metadata travels with it, how attribution and audit work.
  • Content and structure. The decision to model memory as files, how those files are laid out, how skills relate to memory as a form of procedural knowledge.
  • Process. How memory gets updated, what triggers updates, which sources feed into the decision about what to write down.

Storage and content are the easy parts. The process layer, who updates memory and when, is where most existing memory systems fall short.

Single agents update memory from their own perspective: their own context, their own task. That is fine for small deployments and falls over at scale. Sessions miss patterns that other sessions have already figured out. Common mistakes show up in five separate sessions without anyone consolidating. The store gets messy. Old entries hang around past their usefulness. None of this is a flaw in any individual agent. It is a structural gap, and it is what the third act is about.

Act IIIDreaming

The product launching alongside memory is called Dreaming. It is a batch, asynchronous process that runs separately from any individual session. You either fire it on a schedule from the console or kick it off via the API at the end of an agent's work. Dreaming reads recent transcripts in bulk, finds patterns across them, and produces an updated memory state, which you can then apply to the store immediately or review first.

The name is doing some lifting. The conceit is a system that consolidates the day's experiences while no one is looking, the same way sleep is hypothesized to consolidate memory in animals. The mechanism is more prosaic: a separate agent loop with its own clearly-defined objective, fed the recent transcripts of all the other agents.

Why this works where single-agent memory does not

Three design properties make Dreaming interesting from a research and harness perspective.

It runs out of band. An agent working on a task has the agent's own context, the agent's own perspective, the agent's own incentives. Looking back at a transcript from outside the session is a different and complementary view. A single agent will not notice that five sessions over the last three days were all triggered by the same upstream condition. A process that reads all five transcripts will.

It has a clear, separate objective. Anthropic's harness design experience is that agents do better when their goal is discrete. Asking an agent to solve a customer's problem and also keep the memory store tidy is asking for one of those two to get neglected. Dreaming separates "memory quality" as a goal in its own right, with its own agent loop, its own evaluation criteria, its own compute budget. The chat agents stay focused on task completion. The dreaming agent stays focused on memory quality.

It does not add latency. Because the work happens in the background, the hot path of any individual chat is unaffected. Memory gets better between sessions, not during them.

Two analogies that earn their keep

Anthropic's team frames Dreaming through two analogies, both of which are more than rhetorical.

The first is test-time compute. When thinking models were new, the insight was that giving a model more tokens to reason at inference time meant materially better final answers. Dreaming is the same shape applied to memory: spend more tokens off the hot path to keep the store organized, and the agents reading from it later get better outcomes for free. The scaling law that worked for reasoning works for memory curation.

The second analogy is a search index. Search systems pay an up-front cost to keep an index fresh, and that cost is amortized across every query that hits the index thereafter. Dreaming is the index build for memory. One agent does the work of consolidating, deduplicating, verifying, and back-filling, and every downstream agent reading the store benefits.

The result that travels

Harvey, the legal-AI company, deployed Dreaming against one of their legal benchmarks, a realistic legal scenario, and reported a six-fold increase in task completion rate. That is a striking number, the kind that does not happen from a UI polish or a faster cache. It is what a structural fix to the memory loop looks like.

Dreaming is the bridge between intermediate memory stores and the larger-scale knowledge bases that will be common in the next few months.

What it looks like in practice

A site-reliability agent gets paged on a P1 alert. It investigates CPU utilization, traffic patterns, recent pull requests. It writes its findings into its team's read-write memory store as it goes. A few minutes later, a second alert fires the same investigation. A different SRE agent spins up, with access to the same store, and sees a note from its sibling: we already investigated this, here is what we found, here is how to short-circuit your own investigation. The second run is dramatically cheaper in tokens and dramatically faster in latency, not because the model changed but because the second agent had access to what the first had learned.

Run Dreaming over the last week of those SRE sessions and a higher-order insight surfaces: a bunch of the agents were triggered exactly sixty seconds after an upstream CPU spike. None of the individual agents would have noticed, because each only saw its own session. Dreaming notices, writes a single consolidated note pointing at the suspect retry logic, deduplicates five copies of a related observation into one, removes an entry that has gone stale, and adds a verification note saying the rest of the file is still accurate as of this scan. The next day's agents inherit a cleaner, denser, more reliable working memory.

The thesis. Memory becomes load-bearing infrastructure rather than a developer convenience. The shift from "tool an agent occasionally calls" to "shared knowledge base that hundreds of agents read and write" is the change to plan for. Dreaming is what makes that shift tractable, because no individual agent has the context, the incentive, or the compute to do the consolidation work properly. Run that work as a separate process with its own objective and the rest of the system stays focused.

Both memory and Dreaming are available now in the Cloud Managed Agents API. Memory is in public beta. Dreaming is in research preview. The reasonable expectation is that agents start running for days at a stretch, not hours, and that what an agent knows on day three depends on what its peers learned on day one. That is a different operating model from a chatbot. It is the one this primitive was built for.
