agentassist vs virtuele-assistent

Two solutions to the same brief. Which one to keep maintaining and which one to release as open source.

TL;DR. Keep both, but keep them for different jobs. virtuele-assistent is the production-grade Montferland system: full RAG, Airflow scraping, admin database, Helm-deployable. Maintain it for the customer. agentassist is the lightweight reference design: same product surface (multi-tenant chat, admin, PII, streaming, source citations) implemented with one Flask process and an agent-with-tools instead of a RAG stack. It is the candidate for an OSS release.

1What is each thing?

agentassist

This project, deployed on Railway.

  • 1 process: a single Flask + gunicorn container.
  • Per-tenant config.json + context.md on disk: no database.
  • Agent-with-tools: a per-request messages.stream against Claude with web_fetch capped to the tenant's allowed_domains and max_uses=3.
  • No ingestion: no scraping pipeline, no vector store. Knowledge comes from the per-tenant context.md plus live web_fetch.
  • Vanilla HTML/JS frontend for chat (full-screen + bubble) and admin (token auth).
  • 62 unit + integration tests, runs in under 3 seconds, no external services required.

virtuele-assistent

The production Montferland repo.

  • 16 services in docker-compose (Airflow alone is 6 containers: postgres, redis, init, api-server, scheduler, dag-processor, triggerer, worker).
  • Real RAG: Qdrant vector store, hybrid search (semantic + BM25), optional HyDE, cross-encoder reranker.
  • Airflow-scheduled scraping per tenant with chunking and embedding.
  • Two Next.js frontends (chat + admin) on TypeScript, Tailwind, Radix.
  • Kotlin/Ktor backend, Postgres for admin, Helm charts for prod.
  • Langfuse observability, prompt management, BSAT scoring.

3Most efficient and maintainable

"Efficient" and "maintainable" depend on what problem you are solving. The honest answer is: pick by knowledge-base size and team size.

If knowledge base ≤ ~50 KB and the source is one public website

Pick agentassist.

  • One service to run, one language to know, one process to monitor.
  • New tenant = new directory under tenants/, no migrations, no Airflow DAG to author.
  • If the model needs more than the local context, web_fetch handles it. Anthropic enforces the host allowlist; prompt injection cannot redirect the fetch.
  • Tests are unit + integration, no test containers, no external services.
  • Operationally: a single Railway service. No Postgres backup, no Qdrant snapshots, no Airflow scheduler to babysit.

If knowledge base is thousands of pages, or you need PO analytics, or you have an editorial team

Stay on virtuele-assistent.

  • web_fetch on its own is not a retrieval strategy at that scale. You want real RAG with hybrid search and reranking, which virtuele-assistent already has.
  • The Airflow ingestion pipeline gives you scheduled scraping, idempotent updates, and per-tenant collections. Building that into agentassist would erase its main advantage.
  • The admin Next.js app + Postgres state are necessary if multiple editors per tenant are common.
  • Langfuse + BSAT + topic analytics are nontrivial to add to a smaller stack and matter for Product Owners.

Verdict on efficiency + maintainability: For 80 percent of municipal-assistant deployments (one website, modest content), agentassist is meaningfully easier to run and harder to break. For the 20 percent that need real RAG + scheduled scraping + editor workflows, virtuele-assistent earns its complexity.

OSS candidate: agentassist, by a wide margin. It is small, runnable in minutes, and demonstrates the patterns (multi-tenant, PII redaction, streaming, source citations, admin) cleanly enough that a developer can adapt it. virtuele-assistent could be open-sourced, but it would mostly be admired, not used.

5Concrete plan to OSS agentassist

  1. License + repo hygiene. MIT or Apache 2. Add a CONTRIBUTING.md, code of conduct, GitHub Actions for pytest. Strip any sensitive defaults from .env.example.
  2. Position the README. "Multi-tenant agent-based chatbot. One Flask process. Drop a context.md per tenant, set ANTHROPIC_API_KEY, deploy anywhere with a Dockerfile."
  3. Generalize the tenant language. Today the defaults assume Dutch municipalities. Make org type pluggable (e.g. library, school, support-team) with their own default suggestion sets.
  4. Provider abstraction. Wrap the Anthropic() client behind a small LLMProvider interface so contributors can plug OpenAI, Azure, or a local model later. Keeps Anthropic as the default.
  5. Optional RAG mode. Document a "if you outgrow context.md, here is how to plug a vector store" extension point. Do not implement it in core. Refer interested users to virtuele-assistent for the production version.
  6. Examples. Ship two tenants out of the box (one Dutch municipality, one English support-team) so the demo works in two languages.
  7. Brand it. Pick a name that signals the philosophy: agentassist, civichat, or tenantbot. The current name fits.
  8. Cross-link. The README points to virtuele-assistent as the "enterprise-grade upgrade path." Two repos, one design philosophy, different scales.

6What I would NOT port back from virtuele-assistent

Some of the things virtuele-assistent has are valuable in production but would dilute agentassist's main pitch. Resist adding them unless a real OSS user asks.

  • Postgres for admin state. File-based is the whole point.
  • Airflow. A scheduled scraper is its own product. If users want it, document a cron + ingest script extension.
  • Reranker microservice. A second service halves the "easy to run" property.
  • Langfuse. Add a lightweight OpenTelemetry adapter or stick to structured logs.
  • Two separate Next.js apps. One vanilla HTML admin is enough for the OSS demo.

7What I WOULD borrow from virtuele-assistent

  • Draft / publish flow in admin. Today agentassist publishes on save. A "save as draft" toggle is a small change and editor-friendly.
  • Prompt-preview endpoint. Show the editor exactly what system prompt will be sent. One Flask route, one editor button.
  • Tenant-scoped admin passwords. Replace the single ADMIN_PASSWORD with a per-tenant secret store.
  • Markdown rendering in the chat bubble. Bot output has **bold** and links, currently shown as plain text. Add micromark + DOMPurify.
  • Feedback per message. Thumbs up/down written to a JSONL file is two endpoints and is genuinely useful.
  • Component toggles in admin. Even a single "available / maintenance" switch covers most of the use case.
