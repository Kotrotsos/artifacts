Security review: agentassist and virtuele-assistent

Two solutions to the same brief, audited for security posture. Concrete file:line citations, severity tagged P1 (must fix before any exposure), P2 (should fix soon), P3 (nice-to-have).

Headline. agentassist has the stronger security posture and a much smaller blast radius if someone deploys it carelessly. virtuele-assistent has solid defense-in-depth where it matters (server-side PII redaction, inter-service auth, real RAG inside a closed network), but its shipped docker-compose.yml contains weak default secrets that an absent .env file silently uses; that alone is the most pressing issue across either project.

1Scorecards

agentassist

A-
Single Flask service. HMAC-signed server-issued session tokens, four-tier rate limiting on the chat endpoint, per-tenant 24h token budget, concurrent-stream cap, origin pinning per tenant, full security-header set (CSP, X-Frame-Options, Permissions-Policy, Referrer-Policy, X-Content-Type-Options), X-Request-ID on every response, server-side PII redaction in the chat pipeline, DOM-only markdown rendering, web_fetch locked to a per-tenant host allowlist with usage cap. Open: one Anthropic key rotation pending as an operator step, an unused /redact route still exposed, ALLOWED_ORIGINS defaults to *.

virtuele-assistent

C
Strong server-side PII redaction (132 LOC Kotlin service with BSN elfproef), X-API-Key auth between proxy and backend, nginx rate-limit on the chat endpoint (10 r/s, burst 20), per-tenant Qdrant collections preventing cross-tenant data leakage at retrieval. Held back by: weak default secrets baked into docker-compose.yml (a fresh deploy without .env uses them), wide-open CORS (anyHost()), no security headers in nginx, Qdrant published on host ports 6333 and 6334, no TLS termination configured in the repo.

2agentassist findings

P1Anthropic API key not yet rotated
operator action, not in code

The live API key was placed in a local .env file before the project had a .gitignore, and the literal value appeared in development chat logs. The current .gitignore protects it now, but the value should be considered compromised.

Fix: generate a new key in console.anthropic.com, set on Railway with railway variables --service agentassist --set "ANTHROPIC_API_KEY=<new>", revoke the old.

P3Unused /api/{tenant}/redact endpoint still mounted
app.py:api_redact

The frontend redacts inside the chat pipeline; this endpoint is no longer called by any client. It is open, unauthenticated, and returns the redaction result plus pattern-hit counts. A black-box attacker could probe it to learn which BSN/IBAN/phone variants the regex matches.

Fix: remove the route, or apply a rate limit if you intend to keep it as a debugging hook.

P3SESSION_SECRET not set as its own Railway variable
env configuration on Railway

app.py resolves it as SESSION_SECRET = os.environ.get("SESSION_SECRET") or ADMIN_SECRET. Today this is harmless: a stable ADMIN_SECRET backs both. But it means rotating the admin secret (good hygiene) silently invalidates every visitor's session token.

Fix:

railway variables --service agentassist \
  --set "SESSION_SECRET=$(python3 -c 'import secrets;print(secrets.token_hex(32))')"
P3ALLOWED_ORIGINS defaults to *
app.py module init

Acceptable for a single-origin deploy and for the OSS demo. Production embeds should pin to the host site(s) explicitly.

P3In-memory state grows without TTL
agent.py:_histories, ratelimit.py bucket dict, concurrency.py counter dict

None of the in-memory dicts are pruned. On a long-running process with many unique sessions and IPs, memory grows. Not a security issue today, an operational one for long-lived deployments.

What is already right.

  • Session tokens are HMAC-SHA256, server-issued, tenant-bound, with hmac.compare_digest for signature comparison and a 24-hour expiry. Cookie carries Secure; HttpOnly; SameSite=Lax; Path=/api/{tenant}/. Client-supplied session_key in request bodies is ignored.
  • Chat endpoint runs four rate-limit tiers (per IP/min, per IP/hour, per session/min, per tenant/min) plus a per-tenant 24-hour token budget enforced from a JSONL ledger plus a concurrent-stream cap (2 per IP, 20 per tenant). Origin pinning kicks in once allowedOrigins is set on the tenant.
  • web_fetch_20260209 tool declares allowed_domains per tenant with max_uses=3. The allowlist is enforced by Anthropic on the tool-execution side; prompt injection cannot redirect the fetch to an attacker-controlled host.
  • Server-side PII redaction (BSN with Dutch elfproef, IBAN, email, phone, postcode, doc-num) runs before the message reaches the model or the logs.
  • Security headers on every response: CSP, X-Frame-Options DENY, Permissions-Policy, Referrer-Policy no-referrer, X-Content-Type-Options nosniff.
  • Frontend markdown renderer builds DOM via createElement and textContent only. No innerHTML. Link href is filtered through new URL(...) with a protocol allowlist (http, https, mailto); javascript: and data: render as plain text.
  • Tenant ids regex-validated (^[a-z][a-z0-9_-]{1,63}$) before being used in filesystem paths; no path traversal.
  • Request body capped at 64 KB; chat messages capped at 4000 characters.
  • Error responses sanitized: stack-trace-shaped text dropped, generic Dutch fallback, full exception logged with request_id server-side only.
  • 91 tests, run in under 3 seconds, no external services required.

3virtuele-assistent findings

P1Weak default secrets in docker-compose.yml
docker-compose.yml:15-16, :91, :125, :172, :200

The compose file ships with usable defaults: AIRFLOW__API__SECRET_KEY:-super-secret-key-change-me, POSTGRES_PASSWORD:-adminpass123, ADMIN_PASSWORD:-changeme, and a literal POSTGRES_PASSWORD: airflow on the Airflow postgres (no env-var indirection at all). Any environment that skipped a .env step deploys with these in place.

Fix: change every ${VAR:-default} to ${VAR:?error} so the compose fails fast on missing values; remove the literal airflow password.

P1CORS wide open on the backend
agent-backend/src/main/kotlin/Application.kt:99

install(CORS) { ... anyHost() }. Any origin can issue authenticated cross-site requests once a session cookie or token is involved. There is no Origin allowlist on the backend itself; the nginx layer only proxies, it does not restrict origins.

Fix: replace anyHost() with the production frontend origin(s) explicitly.

P1Qdrant published on host ports
docker-compose.yml:73-74   - "6333:6333", - "6334:6334"

On a docker host with a public network interface, Qdrant's REST and gRPC ports are reachable without authentication. An attacker with port access can read or delete any collection.

Fix: drop the host port mapping; keep Qdrant on the internal docker network only. If external admin access is required, put it behind an authenticated reverse proxy.

P2No security headers in nginx
nginx.conf

No Content-Security-Policy, no X-Content-Type-Options, no Referrer-Policy, no X-Frame-Options. The frontends are React; React's default escaping mitigates basic reflected XSS, but a CSP would close the gap against any future inline-script or third-party-dependency injection.

Fix: add add_header directives in nginx, or a top-level map. For an embeddable widget, do an explicit frame-ancestors allowlist of host sites.

P2No TLS termination configured
nginx.conf + compose

The nginx config listens on port 80 only. Behind a managed platform (cloud load balancer, Cloud Run) that terminates TLS, this is fine. The repo as shipped does not include a TLS path; production deploys need to add it (or document the assumption clearly).

P2Large secret surface
.env.example

Production requires Langfuse public + secret keys, OpenAI key, Azure OpenAI key + endpoint + version, Airflow Fernet key, Airflow secret key, admin password, admin DB password, and the inter-service API key. Nine secrets across components. That is many places to leak from and many places to rotate.

Fix: document a rotation runbook. Consider a secrets manager (AWS SSM, Doppler, Vault) so secrets are not all in a single .env file on every developer's machine.

P2PII redaction has a fail-open fallback on the frontend
spec PII-2, frontend redact integration

The frontend posts the user message to /ai/redact before sending it to the chat stream. The spec documents: "Bij redact-fail (404, timeout): fallback naar raw body met error in console; verzoek breekt niet." In worst case unredacted PII reaches the model and Langfuse traces. Defense in depth exists (the backend also redacts before logging), so this is P2 rather than P1.

P3Single global admin password
spec ADMIN-1 (project's own open punt)

Per-tenant credentials are the eventual fix.

What is already right.

  • Server-side PII redaction is its own Kotlin service (132 LOC, six pattern classes including BSN elfproef), invoked on every chat request as defense in depth.
  • Inter-service authentication via X-API-Key: the backend rejects requests without the header (Application.kt:23, Application.kt:114). The proxy adds it; direct calls bypass the proxy and fail.
  • nginx rate-limits the chat endpoint to 10 req/sec/IP with a burst of 20, returning 429.
  • Per-tenant Qdrant collections prevent cross-tenant data leakage at the retrieval layer.
  • .gitignore covers .env properly; no secrets are committed to the repo.
  • Airflow stack and Postgres are on the private Docker network for inter-service traffic.
  • Tenant isolation extends to Langfuse: spec PII-3 calls out that scores and traces are server-side filtered by tenant.

5What this looks like in production

A practical way to think about it: what happens if either project is dropped onto a host with the shipped configuration?

agentassist, shipped configuration

  • Requires ANTHROPIC_API_KEY and (for admin) ADMIN_PASSWORD to be set; otherwise the app refuses to start or the admin login returns 503. Fails closed on missing secrets.
  • If you forget to set SESSION_SECRET and ADMIN_SECRET in the environment, they default to a random value generated at process start; this works but means a process restart invalidates existing tokens. Documented.
  • Anonymous chat is bounded by rate limits and a per-tenant token budget. A scripted abuser can burn at most one tenant's daily budget before the endpoint returns 503.

virtuele-assistent, shipped configuration

  • If you skip the .env step, docker compose up still works. It deploys with POSTGRES_PASSWORD=adminpass123, ADMIN_PASSWORD=changeme, and an Airflow secret literally named super-secret-key-change-me. Anyone with port access can log into the admin DB and the admin UI.
  • Qdrant is exposed on host ports 6333 and 6334 by default. If the host has a public IP, an attacker with port access can read or delete every tenant's collection.
  • The backend accepts any origin once authenticated against the X-API-Key. The X-API-Key is added by nginx for proxied calls; direct calls to the backend on its container port (8080) bypass the proxy.

6If both went to a public URL today

agentassist: one operator action

  1. Rotate ANTHROPIC_API_KEY.

Optionally, before OSS release: remove or rate-limit the unused /redact endpoint, set SESSION_SECRET as its own variable, pin ALLOWED_ORIGINS.

virtuele-assistent: three code changes

  1. Eliminate every ${VAR:-foo} default in docker-compose.yml; replace with ${VAR:?error} so missing values fail fast. Remove the literal POSTGRES_PASSWORD: airflow.
  2. Replace anyHost() with an explicit Origin allowlist in Application.kt:99; add an after hook for security headers (CSP, X-Frame-Options, Referrer-Policy).
  3. Drop the host port mapping for Qdrant in docker-compose.yml; keep it on the internal network. If admin access is needed, terminate behind an authenticated reverse proxy.
Bottom line. Both projects do PII redaction well and isolate tenants at their respective storage layers. The gap is at the deployment boundary. agentassist fails closed on missing configuration and applies modern web-security headers; virtuele-assistent fails open on missing configuration and exposes infrastructure (Qdrant, weak admin defaults) that does not need to be reachable. For an OSS release, where the worst-case operator drops the project on a host without reading the docs, agentassist's posture is materially safer.
