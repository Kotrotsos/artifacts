Problem Statement

Elastofirm develops rubber compounds (EPDM and others) the traditional way: a compounder's experience plus trial-and-error in the lab. Auke Philips scoped a data schema (EPDM_Compound_Structuur.xlsx) as a precondition for "compounding with AI." The goal of THIS project is narrower and more honest than "AI makes recipes": determine whether AI agents can usefully generate novel candidate rubber recipes toward a stated goal, attach honest confidence and evidence, and rank what is worth testing in the lab, including deliberately "out of bounds" ideas like using concrete as a filler.

This is a feasibility question, not a product commitment. The deliverable of the first build is evidence: are the generated candidates good enough that Auke would actually put them on the bench?

What Makes This Cool

  • Out-of-distribution by design. Every commercial materials-informatics tool (Citrine, Uncountable, Polymerize, Albert Invent, Matmerize) optimizes WITHIN a customer's existing dataset. They need clean data first and structurally cannot explore genuinely novel ingredients. An LLM-agent, literature-grounded prior + lab-in-the-loop can start cold AND go out of bounds. That is the wedge.
  • Goal-driven. Set a property envelope ("Shore A 60-70, compression set <20% at 100C, ozone-resistant, cost < X") optionally with a hard constraint ("must use concrete filler"), and the system searches recipe space for candidates that hit it.
  • Honest. It is a hypothesis engine, not an oracle. Output is a ranked shortlist with confidence, citations, and "test this first", not fake-precise property numbers.
  • Demoable. The first version produces a single self-contained HTML dossier you can hand to Rene/Dave/Auke.

Constraints

  • First user is internal: Elastofirm's compounders (Auke first). Distribution is an internal tool / artifact, not a SaaS yet.
  • Little-to-no clean historical recipe→property dataset assumed available at start (to be confirmed, see Open Questions). Design must not depend on it.
  • Property predictions must never be presented as measured truth.
  • Built on agentic, multi-agent workflows (the user's stated architecture).

Premises (all confirmed by user)

  1. It is a hypothesis + experiment-prioritization engine, NOT a property simulator. Output is a ranked shortlist of recipes to test, each with confidence and rationale. It never claims the numbers are true.
  2. The differentiated core is agentic, retrieval-grounded hypothesis generation over out-of-distribution ingredients. The optimization / active-learning math is REUSED from existing work (Bayesian optimization, active learning), not invented.
  3. LLM parametric memory of exact phr values and property numbers is unreliable. The "deep research" must be grounded in retrieved evidence (papers, patents, supplier technical data sheets) with visible citations and uncertainty, or a compounder dismisses it instantly for confidently-wrong numbers.
  4. Feasibility hinges on a real feedback signal. Auke's lab (or a seed of historical results) has to be in the loop, or it stays a brainstorm toy that cannot calibrate.
  5. The unsexy core is representing rubber correctly (ingredient ontology, phr accounting, sulfur vs peroxide cure logic, process params). Bad schema = bad candidates regardless of agent quality. This builds on Auke's xlsx, corrected.

Approaches Considered

Approach A: Single-shot research dossier Chosen core

One workflow. Input a goal (property envelope + optional constraints). Multi-agent deep research (retrieval-grounded) proposes N candidate recipes on the corrected schema, full phr formulation, cure system, process params, predicted properties with qualitative confidence + citations + "test this first". Ranked by distance-to-target × confidence × novelty. Output = one self-contained HTML dossier. No DB, no UI, no feedback loop yet.

Effort S-M workflow + ~3-5d schema/corpusRisk LowReuses corrected schema, Claude agents, retrieval

Approach B: Closed-loop active-learning workbench Deferred

Ingredient/recipe ontology DB + generation agents + surrogate model seeded by the LLM/physics prior, refined as lab results flow back (Bayesian optimization / active learning selects next experiments). UI for goals, candidate review, lab-result logging. All three modes (target / novelty / beat-an-existing).

Effort L-XL (~2-4 mo)Risk MedReuses BoTorch/Ax or scikit-optimize, schema, agent layer from A

Approach C: Constraint-validated agent hybrid Thin slice folded in

Chemical validity as explicit constraints: phr accounting balances, sulfur cure REQUIRES ZnO + stearic acid, filler loading limits, cost ceiling, no-SVHC. Agent does creative ingredient choice + grounding; a rules layer rejects/repairs invalid recipes so the system can't emit nonsense. Valid-by-construction, then ranked.

Effort M (~1d for rules layer)Risk MedReuses reusable in B later

Recommended Approach

Approach A + a thin slice of C. Build the single-shot dossier and a lightweight chemical-validity check. Rationale: the whole go/no-go is "are the candidates good enough that Auke would test them?" A dossier answers that in days and yields a real artifact for the Elastofirm side. The validity check (ZnO / stearic-acid presence for sulfur cure, phr balance, sane loadings, cost ceiling, plus cure-poisoning / chemical-incompatibility checks) costs ~1 extra day and stops the credibility-killing impossible recipes. B is the destination, built only after A validates candidate quality.

What A proves, and what it does NOT (reconciling Premise 4)

Be honest about the staircase. Premise 4 says true feasibility hinges on a calibrated feedback signal. Approach A does NOT deliver calibration, it has no loop. A tests one strictly-necessary precondition: do the agents generate candidates a domain expert finds plausible and worth bench time? If A fails that, nothing downstream matters and you stop cheaply. If A passes, you have earned the right to build B, where lab results actually calibrate confidence. So the feasibility question splits in two: A answers "are the candidates plausible?" (precondition); B answers "are the predictions trustworthy enough to bet lab money?" (the real thing). The success criteria below test only the precondition.

Recommended build shape (for the eng/implementation phase, not built here)

  • Goal spec object: target property envelope (ranges + hard/soft flags), constraints (required/forbidden ingredients, cost ceiling, regulatory), base polymer family.
  • Generation workflow. Start with the SIMPLEST thing that can answer the gate: a single retrieval-grounded agent that proposes, self-validates, and scores. Only decompose into multiple agents (research / formulate / estimate) if the single agent visibly fails. The user's stated multi-agent architecture is the destination, not a v0 requirement, do not pay for orchestration the gate doesn't need. If decomposed:
    • Research agents (parallel, retrieval-grounded): evidence for ingredient choices, analogous compounds, filler/cure interactions.
    • Formulator agent(s): emit candidate recipes on the corrected schema.
    • Validity layer (slice of C): reject/repair recipes that fail phr accounting, cure-system requirements, loading limits, cost ceiling, OR chemical compatibility (e.g. an alkaline/hygroscopic filler like concrete poisoning a sulfur cure, stoichiometry alone will not catch this).
    • Property estimator: a qualitative confidence label (High/Med/Low) per property, NOT a statistical "band" (there is no data to support an interval, calling a subjective guess a "band" is the fake-precision Premise 1/3 warn against). Mark "unknown" where there is no basis.
  • Citation verification (non-negotiable for credibility): retrieve-then-quote. A cited claim must be backed by a quotable snippet from the retrieved source; claims whose source cannot be quoted are dropped or flagged "unsourced." An unverified-but-confident citation is worse than none to a skeptical chemist.
  • Ranking: score = normalized distance-to-target (each property scaled to its own range so Shore A points, compression-set %, and cost are comparable; booleans as pass/fail gates) × confidence, with a novelty term so the pipeline does not just regurgitate the best-documented textbook EPDM (retrieval grounding pulls toward the known; novelty pulls back toward "out of bounds"). Output top N.
  • Reproducibility: record the goal, seed/config, and retrieved sources so a re-run is explainable. Auke re-running and getting wildly different recipes with no explanation erodes trust.
  • Output: self-contained HTML dossier (light-mode default + light/dark/system switch), one card per candidate: formulation table, process + cure params, predicted properties with qualitative confidence, verified citations, "what to test first."

Key Risks (confront before/while building)

  1. Retrieval corpus access, the #1 feasibility risk. The entire "retrieval-grounded" premise collapses if the agents only see open web. Real rubber phr signal lives in patents, supplier TDS, and internal know-how, much of it paywalled or proprietary. Open-web rubber-formulation data is thin and noisy. Resolve corpus access EARLY; if it's open-web-only, grounding quality (and Premise 3) is at risk and the gate may fail for the wrong reason.
  2. Novelty vs. grounding tension. RAG converges on the well-documented; the product's wedge is "out of bounds." These pull opposite directions. The novelty term in ranking is the mitigation, but watch that out-of-bounds candidates actually survive the pipeline and aren't filtered out as "unsupported."
  3. Citation fabrication. LLMs invent plausible citations and misattribute phr values. Mitigated by the retrieve-then-quote verification step above; treat any unverified citation as a bug, not a stylistic nit.
  4. Self-rated confidence is the same unreliable source grading itself. Premise 3 says parametric numbers are untrustworthy; an agent's confidence in those numbers inherits that unreliability. Acceptable ONLY as coarse triage (High/Med/Low) in v0; it is not calibration. This is precisely why B (lab feedback) exists.
  5. Schema correction is real domain work, not a checkbox. Peroxide-cure path, Mooney, de-duplicating oil/plasticizer, activators, getting this right gates everything downstream. Estimated separately; do not bury it in the workflow estimate.

Open Questions

  1. Data reality: How many historical Elastofirm recipes WITH measured properties exist, and in what form (paper, Excel, LIMS)? Even 50-200 rows would meaningfully seed B's calibration loop. (Does not block A.)
  2. Schema correction sign-off: who signs off on the corrected schema (Auke)?
  3. What counts as a pass? The success bar below is a proposal, does Auke agree that "expert would bench-test ≥ K of N" with a baseline is the right gate, and on the N/K values?

Success Criteria (feasibility gate, tests the PRECONDITION only)

  • Run ≥ 3 real goals: one ordinary EPDM target, one cost-down vs an existing Elastofirm compound, one "out of bounds" (e.g. concrete filler).
  • For each goal the system emits N = 5-8 candidates; every emitted candidate passes the chemical-validity check (no impossible recipes survive) and every property prediction carries a qualitative confidence + a verified citation or an explicit "unknown."
  • Baseline arm (to avoid a generous-evaluator false positive): for each goal, also generate candidates from a naive single-LLM prompt (no retrieval, no validity layer). Mix them with the system's candidates and present them to Auke blind (he doesn't know which is which).
  • Primary gate: the expert (Auke) marks at least K ≥ 3 of N of the SYSTEM's candidates per goal as plausible and worth bench time, AND the system beats the blind baseline by a clear margin. Pass → green-light Approach B scoping. Fail → the generation core isn't good enough yet; iterate on retrieval/prompting/validity before building anything heavier.
  • Honest non-goal: this gate does NOT prove the predicted numbers are correct. That is B's job (lab calibration).

Distribution Plan

  • v0 (Approach A): internal artifact. The HTML dossier is the deliverable; runs on Marco's machine / NxtPhase via the workflow tooling. No deployment needed.
  • If B is greenlit: internal web tool for Elastofirm compounders (auth, persisted recipes + lab results). Deployment channel decided at B scoping. Deferred.

Next Steps (concrete build order)

  1. Resolve corpus access (Key Risk 1) and schema correction in parallel, both gate everything.
    • Corpus: confirm what the agents can actually retrieve (open lit/patents only, or supplier TDS + internal know-how).
    • Schema: produce v1 ingredient/recipe ontology from the xlsx with fixes (drop aromatic-oil example, de-duplicate oil/plasticizer, add ZnO + stearic acid, add peroxide-cure path + coagent, add raw-polymer Mooney, restore Batchnummer + test conditions); get Auke's sign-off. Treat this as its own ~3-5 day domain task, NOT folded into the workflow estimate.
  2. Encode the validity rules (slice of C):
    • phr accounting: rubber phr = 100 by definition; non-rubber ingredients are relative to that, check totals fall in a sane envelope, not that they sum to a fixed number.
    • cure-system requirements: sulfur ⇒ ZnO + stearic acid present; peroxide ⇒ coagent present and no sulfur/peroxide conflict.
    • loading limits, cost ceiling, SVHC blocklist.
    • chemical compatibility / cure-poisoning (alkalinity, moisture) for exotic fillers, the check that actually catches a bad concrete recipe.
    • (deferred but noted) reactivity-hazard screen beyond SVHC.
  3. Build the generation workflow, single-agent first (Approach A): one retrieval-grounded agent that proposes → self-validates → estimates (qual. confidence) → verifies citations → ranks (distance × confidence × novelty). Decompose into multiple agents only if the single agent fails the gate.
  4. Render the HTML dossier (light-mode default + light/dark/system switch).
  5. Run the 3 feasibility goals with the blind baseline arm and sit with Auke for the primary-gate judgment.
